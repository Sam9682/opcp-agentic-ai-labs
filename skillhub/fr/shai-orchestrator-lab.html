Atelier : la boucle superviseur du CLI Agent Orchestrator (CAO)

Bac à sable · Orchestration ⏱ ~40 min

Cet atelier pratique pilote le CLI Agent Orchestrator (CAO) — un outil réel que vous installez et exécutez vous-même. CAO coordonne plusieurs CLI de fournisseurs comme une équipe : un agent superviseur découpe un objectif en sous-tâches et les délègue à des agents travailleurs délimités. Au fil de l'atelier, vous installez CAO, démarrez le cao-server, lancez un superviseur dans votre propre répertoire de projet, déléguez une petite tâche, observez l'exécution via le terminal attaché et l'interface web, puis arrêtez l'ensemble. Les commandes de cette page sont réelles et exécutables sur votre propre installation de CAO.

Objectifs pédagogiques

  • Décrire comment CAO est assemblé : un cao-server local qui démarre des CLI de fournisseurs dans des sessions de terminal isolées.
  • Nommer les rôles d'agent — superviseur, travailleur et relecteur — et ce dont chacun est responsable.
  • Expliquer le modèle de délégation : comment une tâche circule du superviseur vers un travailleur et en revient.
  • Exécuter la boucle superviseur de bout en bout depuis la ligne de commande : installer, lancer, déléguer, observer et arrêter.
  • Lire un exemple de profil d'agent CAO et comprendre chaque champ comme une décision de gouvernance.

Prérequis & installation

Avant d'exécuter quoi que ce soit, assurez-vous que votre machine dispose des outils dont CAO dépend. Installez chacun d'eux et confirmez qu'il figure dans votre PATH :

  • Python 3.11+ — CAO fonctionne sous Python 3.11 ou version ultérieure.
  • tmux 3.3+ — CAO démarre chaque CLI de fournisseur dans une session de terminal tmux isolée ; vous avez donc besoin de tmux 3.3 ou version ultérieure.
  • uv — l'installateur de paquets et d'outils Python utilisé pour installer l'outil en ligne de commande cao.
  • Au moins un CLI de fournisseur authentifié — chaque agent est adossé à un CLI de fournisseur doté de sa propre authentification native. Le fournisseur par défaut est le SHAI CLI ; assurez-vous qu'il est installé et connecté avant de lancer un agent.

L'architecture de CAO

CAO n'est pas un agent unique — c'est une couche d'orchestration locale. Le processus cao-server s'exécute sur votre machine et démarre chaque CLI de fournisseur dans sa propre session de terminal tmux isolée, si bien que chaque agent est un processus CLI à part entière avec sa propre authentification native plutôt qu'un sous-processus caché. Par-dessus, un profil superviseur tient l'objectif de haut niveau, le découpe en sous-tâches et délègue chacune à un agent travailleur spécialisé — en parallèle lorsque les sous-tâches sont indépendantes, ou en séquence lorsqu'elles dépendent les unes des autres. Les travailleurs ne communiquent jamais directement entre eux ; tout passe par le superviseur, ce qui garde l'exécution observable et vous offre un point de contrôle unique.

flowchart TD
    U[Operator / CLI] --> S[CAO supervisor]
    S --> W1[Worker agent: developer]
    S --> W2[Worker agent: developer]
    S --> R[Reviewer agent]
    W1 --> S
    W2 --> S
    R --> S
    S --> U

Le superviseur est le pivot : il délègue aux agents travailleurs, achemine les résultats via un relecteur et rend compte à l'opérateur.

Trois éléments font de ceci une conception défendable plutôt qu'une simple diffusion de tâches :

  • Un coordinateur unique. Un seul superviseur tient le plan, donc il existe exactement un endroit qui décide de ce qui s'exécute ensuite et du moment où s'arrêter.
  • Des travailleurs isolés. Chaque travailleur s'exécute comme son propre processus CLI de fournisseur dans une session de terminal isolée, avec un périmètre allowedTools dimensionné à sa tâche, si bien qu'une erreur chez l'un ne peut pas se propager à un autre.
  • Une porte de relecture. Le travail modifiant passe par un agent role: reviewer avant que le superviseur ne l'accepte, gardant un contrôle aligné sur l'humain dans la boucle.

Les rôles d'agent

Une exécution CAO se compose de trois types d'agent, chacun adossé à un profil intégré (code_supervisor.md, developer.md, reviewer.md). Chacun a une seule mission et un périmètre allowedTools dimensionné pour cette mission.

superviseur (code_supervisor)Tient l'objectif de haut niveau, le découpe en sous-tâches, délègue chacune à un travailleur, achemine le travail modifiant via le relecteur, agrège les résultats et décide quand le travail est terminé. N'écrit jamais de code lui-même.Coordination seule : @cao-mcp-server, fs_read, fs_list ; délègue via delegateTools (par défaut ["*"])
travailleur — developer (developer)Exécute une sous-tâche déléguée, autonome — implémente le changement délimité — et renvoie un résultat structuré au superviseur.Lecture/écriture/exécution : fs_*, execute_bash, @cao-mcp-server (@builtin), délimités par sous-tâche
travailleur — reviewer (reviewer)Inspecte l'action modifiante proposée par un travailleur quant à son exactitude, sa qualité et sa sûreté, puis l'approuve ou la rejette avant que le superviseur n'accepte le changement.Lecture seule : fs_read, fs_list, @cao-mcp-server (@builtin)
Gouvernance : le superviseur ne détient délibérément aucun outil hôte d'écriture ou d'exécution — il coordonne et délègue. Les attributions puissantes comme fs_write et execute_bash vivent sur le travailleur developer et sont délimitées par sous-tâche via allowedTools, tandis que delegateTools plafonne ce que le superviseur peut transmettre, si bien que le rayon d'impact de chaque agent reste petit.

Le modèle de délégation

La délégation est le cœur de CAO. L'opérateur confie un objectif au superviseur ; le superviseur décide quel travailleur doit traiter chaque morceau et délègue une sous-tâche autonome. Une sous-tâche déléguée porte tout ce dont le travailleur a besoin et rien de plus :

  • Un énoncé d'objectif — la seule chose que ce travailleur doit accomplir.
  • Des entrées délimitées — uniquement les données pertinentes pour la sous-tâche.
  • Une attribution d'outils — le jeu d'outils minimal pour cette sous-tâche, borné par le plafond delegateTools du superviseur.
  • Un contrat de retour — le résultat structuré que le superviseur attend en retour.

Un travailleur exécute sa sous-tâche et renvoie un résultat structuré au superviseur. Lorsque le travail est modifiant — il change des fichiers ou de l'état — le superviseur achemine ce résultat via un agent relecteur avant de l'accepter ; une sous-tâche en lecture seule revient directement au superviseur. Le cycle de vie d'une seule tâche déléguée ressemble à ceci :

sequenceDiagram
    Operator->>Supervisor: goal
    Supervisor->>Worker: delegate(sub-task, scoped tools)
    Worker->>Worker: run sub-task
    Worker-->>Supervisor: structured result
    Supervisor->>Reviewer: review(result) if mutating
    Reviewer-->>Supervisor: approve / reject
    Supervisor-->>Operator: aggregated outcome

Une sous-tâche en lecture seule revient directement au superviseur ; une sous-tâche modifiante passe d'abord par le relecteur.

Parce que le superviseur est le seul agent qui voit le plan complet, il est aussi le seul endroit qui applique les limites opérationnelles — il ordonne les sous-tâches, relance les délégations échouées et décide quand l'objectif est atteint ou qu'une limite est touchée. Ces contrôles de la boucle superviseur sont la forme, au niveau de l'orchestration, des critères d'arrêt que vous avez rencontrés plus tôt dans le cours.

Pas à pas : la boucle superviseur

Les étapes ci-dessous parcourent une boucle superviseur de bout en bout sur votre propre projet. Exécutez vous-même chaque commande : installez CAO, démarrez le serveur, lancez un superviseur depuis votre répertoire de projet, déléguez une petite tâche, observez son exécution, puis arrêtez-la. Partout où vous voyez /path/to/your/project, remplacez par le chemin absolu du projet dans lequel vous souhaitez que le superviseur travaille.

Étape 1 — Installer CAO et vérifier

Installez l'outil en ligne de commande cao avec uv, puis confirmez qu'il figure dans votre PATH en affichant son aide.

uv tool install git+https://github.com/Sam9682/cli-agent-orchestrator.git@main --upgrade
cao --help

Étape 2 — Installer l'agent superviseur

Installez le profil superviseur intégré pour que cao launch puisse le démarrer.

cao install code_supervisor

Étape 3 — Démarrer le serveur (Terminal A)

Dans un terminal dédié, démarrez cao-server. C'est un processus de longue durée qui démarre chaque CLI de fournisseur dans sa propre session de terminal tmux isolée — laissez-le s'exécuter pour le reste de l'atelier.

cao-server

Étape 4 — Lancer le superviseur (Terminal B)

Dans un terminal séparé, placez-vous dans votre répertoire de projet et lancez le superviseur. Cela vous attache à la session du superviseur pour que vous puissiez lui parler directement.

cd /path/to/your/project && cao launch --agents code_supervisor

Étape 5 — Déléguer une petite tâche

Dans la session superviseur attachée, saisissez un objectif court — gardez-le petit et relisible, par exemple en demandant au superviseur d'apporter un unique changement restreint et bien délimité à votre projet. Le superviseur découpe l'objectif en sous-tâches et les délègue à un agent travailleur ; vous n'appelez pas le travailleur directement.

Étape 6 — Observer l'exécution

Observez la délégation à deux endroits : le terminal de lancement attaché montre l'activité du superviseur et du travailleur à mesure qu'elle se déroule, et l'interface web à l'adresse http://localhost:9889 vous offre une vue visuelle des sessions et de la délégation entre elles.

Étape 7 — Arrêter

Lorsque vous avez terminé, arrêtez l'exécution. Arrêtez une seule session nommée, ou démantelez toutes les sessions d'un coup.

cao shutdown --session {session-name}
cao shutdown --all
Gouvernance : cao shutdown est votre coupe-circuit. cao shutdown --session {session-name} arrête une session ; cao shutdown --all démantèle toutes les sessions que CAO exécute. Comme les travailleurs ne s'exécutent que sous la session du superviseur, l'arrêt stoppe le superviseur et ses travailleurs ensemble — il n'y a aucun agent orphelin à traquer séparément.

Exemples de profils d'agent CAO

Un agent CAO n'est pas un bloc JSON — c'est un fichier Markdown doté d'un en-tête YAML frontmatter et d'un corps Markdown. Le frontmatter déclare l'identité de l'agent et son enveloppe de gouvernance (qui il est, quel fournisseur l'adosse, quels outils il peut utiliser et combien il peut transmettre aux travailleurs) ; le corps est l'invite système qui indique à l'agent comment se comporter. Voici deux profils réels — un superviseur et un travailleur developer — que nous ouvrons ensuite champ par champ.

Profil superviseur (code_supervisor.md)

---
name: code_supervisor
description: Coding Supervisor Agent in a multi-agent system
role: supervisor
provider: shai_cli
delegateTools: ["*"]
---

You are the Coding Supervisor. You never write code yourself. You break a
goal into sub-tasks, delegate each to a worker agent, route mutating work
through the reviewer, and decide when the job is done.

Profil travailleur (developer.md)

---
name: developer
description: Developer Agent in a multi-agent system
role: developer
provider: shai_cli
allowedTools: ["fs_read", "fs_write", "execute_bash", "@cao-mcp-server"]
---

You are a Developer agent. Implement the single scoped sub-task delegated to
you and return a structured result.

name

Décision de gouvernance : le name est l'identifiant stable de l'agent — c'est ainsi que le profil apparaît dans les journaux et les pistes d'audit, et c'est la poignée que vous passez à cao install et à cao launch --agents. Un nom stable et significatif est ce qui permet à un relecteur de relier une exécution au profil exact qui l'a autorisée.

role

Décision de gouvernance : le role est un préréglage de permissions nommé — les valeurs autorisées sont supervisor, developer et reviewer. Choisir un rôle, c'est choisir un ensemble allowedTools par défaut : un superviseur coordonne et délègue, un developer obtient lecture/écriture/exécution pour faire un travail délimité, et un reviewer est en lecture seule par conception. Le rôle est le contrôle de gouvernance à gros grain que vous fixez avant tout autre réglage.

provider

Décision de gouvernance : provider choisit quel CLI de fournisseur authentifié adosse l'agent — ici shai_cli, le SHAI CLI par défaut. Comme les agents restent des processus CLI à part entière avec authentification native, le fournisseur que vous nommez est l'identité et les identifiants sous lesquels s'exécutent les actions de l'agent ; il a donc sa place dans le récit d'audit aux côtés des attributions d'outils.

allowedTools

Décision de gouvernance : allowedTools est la liste d'autorisation d'outils explicite pour l'agent lui-même, et elle remplace les valeurs par défaut du rôle. C'est l'expression concrète du moindre privilège : le developer ci-dessus se voit accorder exactement fs_read, fs_write, execute_bash et les outils @cao-mcp-server — rien de plus. Si une sous-tâche n'a pas besoin d'écrire des fichiers ou d'exécuter des commandes, ne listez pas ces outils dans le profil qui l'exécute.

Gouvernance : le rôle fixe une valeur par défaut raisonnable, mais allowedTools est l'endroit où vous rendez le moindre privilège explicite. Restreignez la liste à exactement ce dont l'agent a besoin ; une liste d'autorisation que vous lisez d'un coup d'œil est une liste qu'un relecteur peut approuver.

delegateTools

Décision de gouvernance : delegateTools est le plafond de délégation — le maximum qu'un agent peut accorder aux travailleurs qu'il crée, jamais plus que cela quel que soit ce que demande le propre profil d'un travailleur. Il vaut par défaut ["*"] pour role: supervisor (un superviseur peut transmettre tout outil qu'il est lui-même autorisé à utiliser) et le propre allowedTools de l'agent pour tout autre rôle. Le superviseur ci-dessus conserve le delegateTools: ["*"] explicite ; le travailleur developer n'en définit aucun, donc son plafond est simplement son propre allowedTools.

Gouvernance : delegateTools est la façon de plafonner le rayon d'impact sur tout un arbre de délégation. Abaisser le delegateTools d'un superviseur sous ["*"] garantit qu'aucun travailleur qu'il engendre ne peut dépasser cette borne — le plafond est appliqué à la délégation, pas à la confiance. Un agent de rôle reviewer (issu de reviewer.md, allowedTools en lecture seule) est ce via quoi le superviseur achemine le travail modifiant avant de l'accepter.

Correspondance de gouvernance

Le vocabulaire de gouvernance vu plus tôt dans le cours n'est pas abstrait ici — chaque concept se rattache à un mécanisme CAO concret que vous avez déjà vu dans cet atelier.

  • Moindre privilège → allowedTools / delegateTools. allowedTools dimensionne l'attribution d'outils propre à chaque agent exactement à ce dont sa tâche a besoin, et delegateTools plafonne le maximum qu'un superviseur peut transmettre aux travailleurs qu'il crée. Ensemble, ils gardent le rayon d'impact de chaque agent aussi petit que le travail le permet.
  • Porte de relecture → un agent role: reviewer. Le travail modifiant est acheminé via un agent de rôle reviewer de CAO (issu de reviewer.md, allowedTools en lecture seule) qui inspecte le changement avant que le superviseur ne l'accepte, gardant un contrôle aligné sur l'humain dans la boucle.
  • Coupe-circuit → cao shutdown. cao shutdown --session {session-name} arrête une session nommée et cao shutdown --all démantèle toutes les sessions que CAO exécute — une façon unique et décisive de stopper une exécution.
  • Limites opérationnelles → contrôles de la boucle superviseur. Le superviseur est le coordinateur unique qui ordonne les sous-tâches, relance les délégations échouées et décide quand l'objectif est atteint ou qu'une limite est touchée ; les restrictions d'outils bornent le rayon d'impact de chaque travailleur. Ce sont là les limites réelles et appliquées d'une exécution CAO.

Points clés

  • CAO coordonne plusieurs CLI de fournisseurs comme une équipe via un superviseur — c'est une couche d'orchestration, pas un agent unique.
  • Trois rôles : un superviseur qui planifie et délègue, un travailleur (developer) qui exécute des sous-tâches délimitées, et un relecteur qui garde le travail modifiant.
  • Une délégation porte un objectif, des entrées délimitées, une attribution d'outils minimale (bornée par delegateTools) et un contrat de retour — rien de plus.
  • Vous pilotez la boucle superviseur depuis la ligne de commande : installer CAO, démarrer cao-server, lancer le superviseur, déléguer une petite tâche, observer l'exécution et l'arrêter.
  • La gouvernance est concrète : le moindre privilège vit dans allowedTools/delegateTools, la porte de relecture est un agent de rôle reviewer, et cao shutdown est le coupe-circuit.
