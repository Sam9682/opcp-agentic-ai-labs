Configurer un agent SHAI avec MCP vers OPCP-EXPLORER

Après-midi · Gouvernance ⏱ ~45 min

Cette leçon vous guide dans la configuration d'un agent SHAI dont l'unique connexion MCP (Model Context Protocol) en stdio atteint la plateforme agentic-ai opcp-explorer. Vous ouvrirez le fichier AGENTS_CONTROL_AGENT_NO_SKILL.config.json champ par champ, câblerez le bloc serveur MCP qui pointe vers la plateforme, lancerez une seule invite de découverte des conteneurs, puis lirez le rapport Container Discovery Results en direct que l'agent renvoie. L'objectif est de vous rendre capable de reproduire vous-même la connexion MCP et d'interpréter — et de gouverner — ce que le rapport de découverte vous apprend.

Objectifs pédagogiques

  • Configurer un agent SHAI à partir du fichier AGENTS_CONTROL_AGENT_NO_SKILL.config.json, champ par champ.
  • Câbler le bloc serveur MCP en stdio qui relie l'agent à la plateforme agentic-ai opcp-explorer.
  • Lancer l'unique invite de découverte qui déclenche un scan de conteneurs en direct.
  • Interpréter le rapport de classification que l'agent renvoie.
  • Appliquer la gouvernance à chaque choix de configuration qui accorde de l'autonomie.

Le fichier AGENTS_CONTROL_AGENT_NO_SKILL.config.json

L'agent est entièrement défini par un seul fichier JSON. Il nomme l'agent, choisit le modèle qui raisonne pour lui, liste les outils intégrés qu'il peut utiliser, fixe la tâche en une ligne qu'il exécute au lancement, plafonne sa génération et câble son unique connexion MCP. Voici le fichier complet, que nous ouvrons ensuite champ par champ.

{
  "name": "AGENTS_CONTROL_AGENT_NO_SKILL",
  "description": "SHAI agent that discovers and classifies the containers running on the opcp-explorer platform over a single MCP connection.",
  "llm_provider": {
    "provider": "ovhcloud",
    "model": "Qwen3.5-397B-A17B",
    "mode": "FunctionCall"
  },
  "tools": ["read", "write", "bash"],
  "system_prompt": "Call agent_control_containers with live=true and list the containers",
  "max_tokens": 8192,
  "temperature": 0.3,
  "compaction": {
    "enabled": true,
    "trigger_tokens": 6144,
    "keep_last_messages": 6
  },
  "verification": {
    "enabled": false
  },
  "mcp_servers": {
    "opcp-explorer": {
      "command": "/home/ubuntu/agentic-ai-plateform/.venv/bin/python",
      "args": ["/home/ubuntu/agentic-ai-plateform/src/mcp_interface.py"],
      "enabled_tools": ["*"],
      "required": false
    }
  }
}

Identité : name et description

Le champ name étiquette l'agent dans les journaux, les tableaux de bord et les pistes d'audit ; description énonce sa raison d'être en une phrase lisible. Le nommage n'est pas cosmétique — lorsqu'un agent agit sur des déploiements réels, un nom clair et stable est ce qui permet à un relecteur de remonter d'une action à la configuration qui l'a autorisée.

llm_provider

Le bloc llm_provider choisit le modèle qui raisonne pour l'agent : fournisseur ovhcloud, modèle Qwen3.5-397B-A17B et mode FunctionCall. Le mode FunctionCall permet au modèle d'invoquer directement les outils et les fonctions MCP plutôt que de seulement produire du texte, ce qui rend l'appel de découverte possible.

Gouvernance : choisir un modèle et un fournisseur est une décision de politique, pas seulement technique. Épingler l'inférence sur le modèle Qwen3.5-397B-A17B hébergé par OVHcloud maintient le raisonnement sur une plateforme connue et responsable — un élément de la configuration que vous validez, pas une pensée après coup.

Outils intégrés : read, write et bash

Le tableau tools accorde à l'agent trois capacités intégrées : read inspecte les fichiers, write les crée ou les modifie, et bash exécute des commandes shell sur l'hôte. Ensemble, ils permettent à l'agent d'accomplir un travail réel plutôt que d'en parler seulement.

Gouvernance : write et bash sont ici les deux attributions puissantes — l'une modifie des fichiers, l'autre exécute des commandes. Ne les accordez que lorsque la tâche l'exige, restreignez leur périmètre d'action et gardez leur activité observable pour que chaque changement laisse une trace.

system_prompt

Le system_prompt est l'unique instruction permanente que l'agent exécute au lancement : Call agent_control_containers with live=true and list the containers. L'argument live=true force un scan à la demande de la plateforme plutôt que de renvoyer un résultat en cache, de sorte que le rapport reflète la flotte telle qu'elle est maintenant.

Limites de génération : max_tokens (8192) et temperature (0.3)

max_tokens plafonne une génération unique à 8192 jetons, bornant ce que l'agent peut produire en un tour. temperature à 0.3 garde la sortie concentrée et reproductible — une température basse convient à un agent d'exploitation, où l'on veut que la même entrée produise la même action prévisible plutôt qu'une variation créative.

Bloc de compaction

Le bloc compaction maintient les longues sessions dans la fenêtre de contexte du modèle : une fois que la conversation dépasse trigger_tokens, les tours plus anciens sont résumés tandis que les messages les plus récents (keep_last_messages) sont conservés tels quels. Cela permet à l'agent de mener un travail en plusieurs étapes sans perdre le fil ni déborder la fenêtre.

Vérification désactivée

Le bloc verification est réglé sur enabled: false, de sorte que la sortie de l'agent n'est pas soumise à une passe de vérification supplémentaire avant d'être renvoyée.

Gouvernance : désactiver la vérification supprime un garde-fou. C'est un compromis délibéré et assumé — acceptable pour une tâche de découverte en lecture seule où la vitesse compte, mais à consigner et à réexaminer avant que le même agent ne soit autorisé à effectuer des opérations qui modifient l'état.

Se connecter à OPCP-EXPLORER via MCP

Un seul serveur MCP en stdio relie l'agent à la plateforme opcp-explorer. La plateforme s'exécute comme un processus Python local que l'agent lance et avec lequel il dialogue via l'entrée/sortie standard — aucun port réseau, aucun service séparé à gérer. Le bloc ci-dessous constitue l'intégralité de la connexion.

"mcp_servers": {
  "opcp-explorer": {
    "command": "/home/ubuntu/agentic-ai-plateform/.venv/bin/python",
    "args": ["/home/ubuntu/agentic-ai-plateform/src/mcp_interface.py"],
    "enabled_tools": ["*"],
    "required": false
  }
}

Le champ command pointe vers l'interpréteur Python de l'environnement virtuel de la plateforme, et args lui transmet le point d'entrée mcp_interface.py ; ensemble, ils démarrent le serveur MCP OPCP-EXPLORER comme un processus enfant. enabled_tools vaut ["*"] et required vaut false.

Gouvernance : enabled_tools: ["*"] accorde à l'agent tous les outils que le serveur expose, présents et futurs — pratique, mais c'est l'opposé du moindre privilège, alors confirmez que la surface d'outils complète est bien celle que vous acceptez. required: false permet à l'agent de démarrer même quand le serveur est hors service : commode pour la résilience, mais une connexion manquante échoue silencieusement au lieu d'arrêter l'agent, et c'est donc à vous de détecter ce cas.

Lire le rapport de découverte

Une fois l'agent lancé, son system_prompt déclenche un unique appel agent_control_containers avec live=true, et le serveur MCP OPCP-EXPLORER répond par un rapport Container Discovery Results (Live Scan). Le rapport parcourt la flotte gérée, classe chaque conteneur qu'il trouve et vous indique ceux qui ressemblent à des agents en cours d'exécution. Le reste de cette leçon lit ce rapport section par section.

Résumé du scan

Le scan en direct a atteint 48 conteneurs sur opcp-psmc-platform (server_id 4) et les a rapportés en totalité. Il a aussi enregistré 1 erreur de scan sur server_id 5 : le serveur n'a pas pu être inspecté à cause d'un échec d'authentification SSH, de sorte qu'aucun de ses conteneurs n'apparaît dans les résultats.

Gouvernance : un serveur injoignable est un angle mort, pas un serveur vide. Le rapport n'est complet que pour les serveurs qui ont répondu — server_id 5 n'a rien renvoyé parce que le scan ne s'est jamais authentifié, alors traitez ses conteneurs comme inconnus plutôt qu'absents jusqu'à ce que l'identifiant SSH soit corrigé et le scan relancé.

Répartition des classifications

Sur les 48 conteneurs scannés, le classifieur a renvoyé 4 conteneurs probable_agent (confiance 0.60–1.00) et 44 conteneurs unclassified (confiance 0.00–0.40). Le classifieur est une heuristique pure et explicable — un conteneur obtient le score probable_agent dès que ses indices franchissent le seuil (score >= 0.5), et chaque point du score a une raison nommée que vous pouvez auditer.

Constats notables et recommandations

En lisant le rapport dans son ensemble, quelques éléments se détachent :

  • L'agent au plus haut niveau de confiance est l'interface web SHAI (ai-shai-web-interface-app-25-8529, 1.00) — la pièce maîtresse attendue de la pile.
  • Les 44 conteneurs restants sont unclassified, ce qui est cohérent avec une infrastructure ordinaire (bases de données, proxies, workers) plutôt qu'avec des agents.
  • server_id 5 n'a pas pu être scanné du tout, de sorte que sa posture en matière d'agents est inconnue.

À partir de ces constats, le suivi recommandé est :

  • Enquêter sur l'identifiant SSH de server_id 5 et le réparer, puis relancer le scan avec live=true afin que la vue de la flotte soit complète.
  • Confirmer que les quatre agents probables sont attendus, et que le signalement du datastore à 0.65 est compris comme un service de support plutôt qu'un agent intrus.
  • Contrôler par échantillonnage une partie des conteneurs unclassified pour s'assurer qu'aucun n'est un agent à faible signal juste sous le seuil.
Gouvernance : la découverte et la classification sont en lecture seule — l'agent inspecte et rapporte, donc l'exécuter est sans danger. Le risque apparaît au suivi : tout stop, restart ou start agit sur des conteneurs en direct et peut mettre hors service un agent — ou un service. Gardez un humain dans la boucle pour chacune de ces actions, conformément aux leçons de l'après-midi sur le Human-in-the-Loop et politique IA OVHcloud et les Garde-fous : cinq couches.
