Atelier : exploitation des applications OPCP-EXPLORER

Bac à sable · Débutant ⏱ ~90 min

Cet atelier pratique unique regroupe l'intégralité du cycle d'exploitation d'OPCP-EXPLORER, auparavant réparti sur sept leçons de bac à sable distinctes. Vous installerez l'Agentic-AI-Platform sur un serveur bare-metal Ubuntu, enregistrerez et démarrerez des applications, les arrêterez proprement, sauvegarderez et restaurerez leurs bases de données, les modifierez avec l'assistance de l'IA, et gouvernerez les agents qui pilotent chacune de ces actions. Chaque section ci-dessous correspond à un ancien sujet : rien du contenu d'origine n'est perdu, il est simplement organisé en un seul atelier cohérent.

Comment utiliser cet atelier : parcourez les sections dans l'ordre lors de votre première lecture. Chaque section indique ses prérequis, ce que vous allez apprendre, les commandes concrètes et la compétence d'agent qui automatise l'action. Toutes les commandes d'exemple et toutes les invites de compétence sont illustratives : lisez-les pour comprendre ce que l'agent exécute en votre nom.

Sommaire de l'atelier

  1. Installation sur Ubuntu bare-metal
  2. Ajouter de nouvelles applications
  3. Démarrer des applications
  4. Arrêter des applications
  5. Réaliser des sauvegardes (et restaurer)
  6. Modifier des applications
  7. Piloter les agents IA

1. Installation sur Ubuntu bare-metal

Déployez l'Agentic-AI-Platform sur un serveur bare-metal Ubuntu neuf (22.04 ou 24.04 LTS), de la préparation du système au déploiement final.

Prérequis

  • Une installation propre d'Ubuntu 22.04 ou 24.04 LTS
  • Un accès root ou sudo
  • Au moins 4 Go de RAM et 20 Go d'espace disque
  • Une connexion Internet pour le téléchargement des paquets
  • Un GPU compatible NVIDIA (facultatif, pour la prise en charge MIG)

Installation rapide

Le moyen le plus rapide de déployer la plateforme est le script automatisé init_pltf.sh, qui exécute chaque étape pour vous et met en place le plan de contrôle de la plateforme Agentic AI. Le script se trouve à la racine du dépôt dédié à la plateforme sur GitHub : github.com/Sam9682/agentic-ai-plateform.

git clone https://github.com/Sam9682/agentic-ai-plateform.git
cd agentic-ai-plateform
# init_pltf.sh is here, in the repository root:
ls -l init_pltf.sh
chmod +x init_pltf.sh
./init_pltf.sh
Note : exécutez le script depuis la racine du dépôt, toujours avec le préfixe ./. Il demande l'identité de la plateforme (slug du dossier, nom affiché, URL du dépôt) et écrit PLTF_NAME / PLTF_FOLDER dans conf/deploy.ini. Appuyez sur Entrée pour accepter les valeurs par défaut, ou pré-renseignez-les via des variables d'environnement pour une exécution non interactive.
Installation manuelle (facultatif)

Voici les étapes individuelles que le script automatisé réalise. Ne les suivez que si vous souhaitez une installation pas à pas ou si vous devez personnaliser le processus.

Étape 1 : installer les dépendances système

sudo apt update
sudo apt --fix-broken install -y
sudo apt install -y python3 python3-pip python3-venv net-tools unzip

Étape 2 : installer les outils CLI (shai et Terraform)

# OVH CLI (shai)
curl -fsSL https://raw.githubusercontent.com/ovh/shai/main/install.sh | sh
echo 'export PATH="~/.local/bin:$PATH"' >> ~/.bashrc

# Terraform
curl -s "https://releases.hashicorp.com/terraform/1.14.5/terraform_1.14.5_linux_amd64.zip" -o "terraform.zip"
unzip -q terraform.zip
sudo mv terraform /usr/local/bin/
rm -f terraform.zip

Étape 3 : configuration réseau (Netplan)

Le script configure les priorités d'interface afin que l'interface publique soit préférée pour le routage par défaut : route de l'interface publique avec une métrique 50 (priorité élevée), route de l'interface privée avec une métrique 200 (priorité basse). La détection des interfaces est automatique (plages privées 10.x, 172.16-31.x, 192.168.x).

Avertissement : une sauvegarde du fichier netplan existant est créée automatiquement avant toute modification.

Étape 4 : installer Docker

curl -fsSL https://get.docker.com -o get-docker.sh
sudo sh get-docker.sh
sudo usermod -aG docker $USER
sudo curl -sL "https://github.com/docker/compose/releases/latest/download/docker-compose-$(uname -s)-$(uname -m)" -o /usr/local/bin/docker-compose
sudo chmod +x /usr/local/bin/docker-compose
rm -f get-docker.sh
Note : déconnectez-vous puis reconnectez-vous pour que l'appartenance au groupe docker prenne effet.

Étape 5 : installer les pilotes NVIDIA et la prise en charge GPU (facultatif)

sudo apt install -y nvidia-driver-550 nvidia-utils-550
sudo nvidia-smi -mig 1
sudo apt install -y nvidia-container-toolkit
docker run --rm --gpus '"device=0"' nvidia/cuda:12.3.0-base-ubuntu22.04 nvidia-smi
Note : le mode MIG n'est disponible que sur les GPU NVIDIA A100, A30, H100 et similaires ; il est ignoré sur le matériel incompatible.

Étape 6 : configurer AWS (stockage S3 OVH)

mkdir -p ~/.aws
cat > ~/.aws/config <<EOF
[profile OVH-SWAUTOMORPH]
region = gra
output = json
EOF
cat > ~/.aws/credentials <<EOF
[OVH-SWAUTOMORPH]
aws_access_key_id = YOUR_ACCESS_KEY
aws_secret_access_key = YOUR_SECRET_KEY
endpoint_url = https://s3.gra.io.cloud.ovh.net/
signature_version = s3v4
EOF
export AWS_DEFAULT_PROFILE=OVH-SWAUTOMORPH
export AWS_ENDPOINT_URL_S3=https://s3.gra.io.cloud.ovh.net/

Étape 7 : cloner le dépôt

git clone https://github.com/Sam9682/opcp-agentic-ai-labs.git
cd opcp-agentic-ai-labs
git submodule update --init --recursive

Étape 8 : mettre en place l'environnement Python

python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

Étape 9 : configuration finale

mkdir -p logs
chmod +x setup_modsecurity_config.sh
cd ~
mkdir -p deployments/admin
Liste de vérification post-installation — n'oubliez pas de :
  • Modifier ./conf/deploy.ini avec les paramètres de votre plateforme, en particulier PLTF_NAME et DOMAIN
  • Ajouter le certificat SSL dans ~/opcp-agentic-ai-labs/ssl/fullchain_domain.crt et la clé privée dans ~/opcp-agentic-ai-labs/ssl/privateKey_domain.key pour le HTTPS de nginx
  • Renseigner aws_access_key_id et aws_secret_access_key dans ~/.aws/credentials pour la synchronisation S3

2. Ajouter de nouvelles applications

Enregistrez et déployez des applications sur la plateforme à l'aide de la CLI, de l'API REST ou de l'interface web d'administration. L'administration web expose une table Applications Management qui liste chaque application enregistrée avec son ID, son nom, son URL, sa description, son URL Git, la taille du dépôt et les temps de build/démarrage/arrêt/ps, ainsi que les actions Edit et Delete.

Méthode 1 : interface web

  1. Connectez-vous à l'interface d'administration
  2. Ouvrez le menu Applications dans la barre de navigation supérieure
  3. Cliquez sur Add New Application
  4. Remplissez le formulaire : Nom (technique, sans espaces, en minuscules), Description, URL et URL Git
  5. Soumettez le formulaire

Méthode 2 : CLI

cd ~/opcp-agentic-ai-labs
source .venv/bin/activate
python opcp-explorer.py add-app \
  --name "my-application" \
  --description "My application description" \
  --git-url "git@github.com/user/my-application.git" \
  --url "https://my-domain.com/admin/my-application"

Méthode 3 : API REST

curl -X POST https://<your-domain>/api/applications \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer <your-token>" \
  -d '{
    "name": "my-application",
    "description": "My application description",
    "git_url": "git@github.com/user/my-application.git",
    "url": "https://my-domain.com/admin/my-application"
  }'
Avertissement : la suppression d'une application est irréversible. Assurez-vous d'avoir une sauvegarde avant de poursuivre.

3. Démarrer des applications

Démarrez une application enregistrée, comprenez l'orchestration de ses conteneurs Docker, surveillez les journaux de démarrage et vérifiez son état de santé.

# Navigate to the platform directory
cd ~/opcp-agentic-ai-labs

# Start an application
./deployApp.sh <app_name>

# Verify the running containers and tail logs
docker ps
docker logs <container_name> --tail 50

Configuration de la compétence : START_APP

Le démarrage d'une application est piloté par la compétence d'agent START_APP. L'invite ci-dessous est la configuration exacte que l'agent suit pour déployer et démarrer une application. Les jetons tels que {{APPLICATION_FOLDER}} et {{USER_ID}} sont remplacés par des valeurs concrètes à l'exécution.

Voir l'invite de la compétence START_APP (SKILL.md) 
You are an autonomous IT Operater agent with access to execute shell commands on a Linux server.
Please deploy and start the application by executing the following steps in sequence.
IMPORTANT :
- all commands have to be executed in the application located {{APPLICATION_FOLDER}}.
- Execute all steps to deploy with the environment variable USER_ID={{USER_ID}}

#### 1. Check Prerequisites (docker and docker-compose must be installed):
command -v docker || exit 1
command -v docker-compose || exit 1

#### 2. Calculate HTTP Ports used by the application's containers:
source {{APPLICATION_FOLDER}}/conf/deploy.ini
RANGE_START=${RANGE_START:-6000}
RANGE_RESERVED=${RANGE_RESERVED:-100}
RANGE_PORTS_PER_APPLICATION=${RANGE_PORTS_PER_APPLICATION:-12}
if ! [[ "$USER_ID" =~ ^[0-9]+$ ]]; then USER_ID=0; fi
PORT_RANGE_BEGIN=$((RANGE_START + USER_ID * RANGE_RESERVED))
base=$((PORT_RANGE_BEGIN + APPLICATION_IDENTITY_NUMBER * RANGE_PORTS_PER_APPLICATION))

#### 3. Generate Secrets (only if .env.prod doesn't exist), build .env.prod with
# POSTGRES_* credentials, DATABASE_URL, JWT_SECRET, DOMAIN and API_URL, then chmod 600 .env.prod

#### 4. Generate Nginx Configuration from conf/nginx.conf.template if it exists.

#### 5. Start the docker services:
docker-compose -p "$NAME_OF_APPLICATION-$USER_ID-$HTTPS_PORT" -f docker-compose.yml --env-file .env.prod up -d

#### 6. Configure Firewall (UFW) to allow the calculated HTTP/HTTPS ports.

#### 7. Verify the service is up:
curl -f -s "https://${DOMAIN}:${HTTPS_PORT}/" || true

Finally, display the link to the web site: https://${DOMAIN}:${HTTPS_PORT}

4. Arrêter des applications

Arrêtez proprement une application, comprenez le processus d'extinction et nettoyez les ressources par la suite.

# Stop a specific application
cd ~/deployments/<app_name>
docker-compose down

# Stop with volume cleanup (removes data)
docker-compose down -v

# Stop the entire platform
cd ~/opcp-agentic-ai-labs
docker-compose down
Avertissement : l'option -v supprime les volumes et les données associés. Créez toujours une sauvegarde avant de l'utiliser.

Configuration de la compétence : STOP_APP

L'arrêt d'une application est piloté par la compétence d'agent STOP_APP, qui effectue un arrêt propre des conteneurs Docker en cours d'exécution pour l'application.

Voir l'invite de la compétence STOP_APP (SKILL.md) 
Please stop all running Docker containers for the specified user instance.
IMPORTANT :
- all commands have to be executed in the application located {{APPLICATION_FOLDER}}.
- Execute all steps with the environment variable USER_ID={{USER_ID}}

#### 1. Calculate HTTP Ports (same port-calculation logic as START_APP).

#### 2. Stop the running application by container name pattern:
echo "Stopping {{APPLICATION_NAME}} services..."
containers=$(docker ps -q --filter "name=${NAME_OF_APPLICATION}-.*-${USER_ID}-.*")
if [[ -n "$containers" ]]; then
    docker stop $containers
    docker rm $containers
    echo "Services stopped successfully"
else
    echo "No running containers found for USER_ID: $USER_ID"
fi

After completion, verify networks are removed, volumes are preserved, and report the final status.

5. Réaliser des sauvegardes (et restaurer)

Sauvegardez les bases de données applicatives vers le stockage objet compatible S3 d'OVH, restaurez-les au besoin et nettoyez une base de données en toute sécurité. Le cycle de sauvegarde : extraire la base avec pg_dump, synchroniser le dump vers OVH S3, le télécharger quand c'est nécessaire, puis le restaurer dans le conteneur de base de données.

flowchart LR
    DB[(PostgreSQL in container)] -->|pg_dump| Dump[backup_YYYYMMDD.sql]
    Dump -->|aws s3 sync| S3[(OVH S3 bucket)]
    S3 -->|aws s3 cp| Local[restore.sql]
    Local -->|psql| DB2[(PostgreSQL in container)]

Le cycle de sauvegarde : extraction, synchronisation vers OVH S3, téléchargement et restauration.

# Backup a PostgreSQL database
docker exec <db_container> pg_dump -U postgres <database> > backup_$(date +%Y%m%d).sql

# Sync backups to OVH S3 object storage
aws s3 sync ./backups/ s3://<bucket_name>/backups/ \
  --profile OVH-SWAUTOMORPH \
  --endpoint-url https://s3.gra.io.cloud.ovh.net/

# Download and restore
aws s3 cp s3://<bucket_name>/backups/backup_20240101.sql ./restore.sql \
  --profile OVH-SWAUTOMORPH \
  --endpoint-url https://s3.gra.io.cloud.ovh.net/
docker exec -i <db_container> psql -U postgres <database> < restore.sql

Configuration de la compétence : BACKUP_DATABASE

L'action de sauvegarde de base de données est pilotée par la compétence d'agent BACKUP_DATABASE, qui extrait la base PostgreSQL et téléverse l'archive vers OVH S3.

Voir l'invite de la compétence BACKUP_DATABASE (SKILL.md) 
You are an autonomous IT Operater agent with access to execute shell commands on a Linux server.
Please backup the PostgreSQL database by executing these steps:
- Backups are stored in OVH S3 using IPv4 addressing
- The S3 bucket path follows: s3://bucket-name/{{APPLICATION_NAME}}/{{IPv4_ADDRESS}}/backups/

#### 1. Check Prerequisites: docker, docker-compose, aws cli.
#### 2. Retrieve DB configuration (DB_CONTAINER, DB_NAME, DB_USER) from docker-compose.yml, falling back to .env.prod.
#### 3. Get the server IPv4 address.
#### 4. Create ./backups and a dated backup file name.
#### 5. Execute the backup:
docker exec $DB_CONTAINER pg_dump -U $DB_USER $DB_NAME | gzip > $BACKUP_FILE
#### 6. Upload to OVH S3:
aws s3 cp $BACKUP_FILE "s3://${S3_BUCKET}/${NAME_OF_APPLICATION}/${SERVER_IP}/backups/" --acl private
#### 7. Record the backup in deployment history.
#### 8. Clean up local backups older than 7 days.

Finally, display the backup file, S3 location, size, and deployment id.

Configuration de la compétence : RESTORE_DATABASE

L'action de restauration est pilotée par la compétence d'agent RESTORE_DATABASE, qui télécharge une sauvegarde depuis OVH S3 et la restaure dans PostgreSQL après avoir réalisé une sauvegarde de sécurité.

Voir l'invite de la compétence RESTORE_DATABASE (SKILL.md) 
You are an autonomous IT Operater agent with access to execute shell commands on a Linux server.
Please restore the PostgreSQL database by executing these steps:
#### 1. Check Prerequisites: docker, docker-compose, aws cli.
#### 2. Retrieve DB configuration from docker-compose.yml / .env.prod.
#### 3. Get the server IPv4 address.
#### 4. List available backups from OVH S3.
#### 5. Download the backup (defaults to the latest if {{BACKUP_FILE}} is not specified).
#### 6. Stop application services to prevent conflicts.
#### 7. Create a safety backup of the current database.
#### 8. Drop and recreate the database.
#### 9. Restore from the backup file:
gunzip -c $LOCAL_BACKUP_FILE | docker exec -i $DB_CONTAINER psql -U $DB_USER -d $DB_NAME
#### 10. Restart application services.
#### 11. Verify the database connection.

On failure, automatically restore from the safety backup.

Configuration de la compétence : CLEAN_DATABASE

L'action de nettoyage est pilotée par la compétence d'agent CLEAN_DATABASE, qui crée une sauvegarde de sécurité puis supprime et recrée la base de données.

Voir l'invite de la compétence CLEAN_DATABASE (SKILL.md) 
You are an autonomous IT Operater agent with access to execute shell commands on a Linux server.
Please clean the PostgreSQL database by executing these steps:
- This operation drops and recreates the database, removing all data; a safety backup is created first.

#### 1. Check Prerequisites: docker, docker-compose.
#### 2. Retrieve DB configuration from docker-compose.yml / .env.prod.
#### 3. Verify the database container is running.
#### 4. Create a safety backup before cleaning.
#### 5. Stop application services.
#### 6. Terminate active database connections.
#### 7. Drop and recreate the database.
#### 8. Apply initial schema from ./scripts/init if present.
#### 9. Restart application services.
#### 10. Verify the database is clean and accessible.

Finally, report the database name, safety backup location, size, and status.

6. Modifier des applications

Utilisez des outils propulsés par l'IA (la CLI Shai) pour modifier, personnaliser et étendre les applications déployées. Le flux assisté par l'IA : décrire le changement, relire le code généré, le valider en préproduction, revenir en arrière en cas d'échec, puis déployer en production une fois le test réussi.

flowchart TD
    Identify[Identify the app and the change needed] --> Describe[Describe the change to Shai CLI]
    Describe --> Review[Review the generated code changes]
    Review --> Staging[Apply and test in a staging environment]
    Staging --> OK{Tests pass?}
    OK -->|no| Rollback[Roll back the change] --> Describe
    OK -->|yes| Prod[Deploy to production]

Le flux de modification assisté par l'IA.

  1. Identifier l'application et le changement nécessaire
  2. Décrire la modification à la CLI Shai
  3. Relire les modifications de code générées
  4. Appliquer et tester dans un environnement de préproduction
  5. Déployer en production une fois validé (revenir en arrière en cas d'échec)

Configuration de la compétence : MODIFY_CODE / KILL

Lorsqu'une modification exige un arrêt immédiat, la compétence KILL termine de force les conteneurs de l'application (SIGKILL) et les supprime tout en préservant les volumes nommés — contrairement à l'arrêt propre de STOP_APP.

Voir l'invite de la compétence KILL (SKILL.md) 
You are an autonomous Operations agent running on a Linux server.
This skill forcefully kills all running Docker containers of a deployed application
instance for a given user (docker kill / SIGKILL), then removes the dead containers.
Named volumes and data are preserved; unsaved in-memory state is lost.

#### 1. Calculate HTTP Ports (same logic as START_APP).
#### 2. Identify the target containers by name pattern ${NAME_OF_APPLICATION}-.*-${USER_ID}-.*.
#### 3. Forcefully kill and remove the containers:
docker kill $containers
docker rm -f $containers
#### 4. Verify no matching containers remain and report the result.

Use KILL only when an immediate termination is required.

Configuration de la compétence : VERIFY_APP_COMPLIANCE

La vérification de conformité est pilotée par la compétence d'agent VERIFY_APP_COMPLIANCE, qui audite une application au regard de l'architecture de la plateforme ai-swautomorph et produit un rapport de conformité assorti d'un score.

Voir l'invite de la compétence VERIFY_APP_COMPLIANCE (SKILL.md) 
You are an autonomous compliance verification agent on a Linux server.
Goal: verify whether {{APPLICATION_FOLDER}} is compliant with the ai-swautomorph
platform architecture (reference at ~/ai-swautomorph).

#### 1. Verify ~/ai-swautomorph exists.
#### 2. Analyze the platform requirements (docker-compose.yml, deployApp.sh, conf/deploy.ini, nginx, SSL).
#### 3. Analyze the current application structure.
#### 4. Compare and identify gaps: compliant / missing / non-compliant components and configuration issues.
#### 5. Check docker-compose.yml compliance (port mappings, volumes, networks, USER_ID naming).
#### 6. Check deployApp.sh compliance (start/stop/restart/ps/logs, port calculation, SSL, firewall).
#### 7. Generate a compliance score (e.g. "65% (13/20 requirements met)").
#### 8. Provide actionable recommendations with priority and complexity.
#### 9. Generate a summary report.

Be thorough, reference swautomorph examples, and prioritize by deployment impact.

Configuration de la compétence : MAKE_APP_COMPLIANT

La remédiation est pilotée par la compétence d'agent MAKE_APP_COMPLIANT, qui modifie les fichiers de déploiement d'une application (uniquement l'infrastructure, jamais la logique métier) pour la rendre conforme à l'architecture de la plateforme, en validant les changements sur une branche dédiée.

Voir l'invite de la compétence MAKE_APP_COMPLIANT (SKILL.md) 
You are an autonomous compliance remediation agent on a Linux server.
Goal: modify {{APPLICATION_FOLDER}} to be fully compliant with the ai-swautomorph
platform architecture (reference at ~/ai-swautomorph).

#### 1. Verify ~/ai-swautomorph exists and run a compliance check first.
#### 2. Ensure the git working tree is clean; create a compliance branch.
#### 3. Copy/create docker-compose.yml with correct port variables and USER_ID container naming.
#### 4. Add ai-swautomorph-shared as a git submodule and symlink deployApp.sh -> ./shared/deployApp.sh.
#### 5. Create/update conf/deploy.ini, conf/nginx.conf.template, ssl/, .env.prod template.
#### 6. Set executable permissions, test config loading, re-run the compliance check.
#### 7. Stage, commit, and push the changes; generate a remediation report.

CRITICAL: do NOT modify application business logic, schemas, data, or app-specific
env vars. ONLY add or update deployment infrastructure files.

7. Piloter les agents IA

Accorder de l'autonomie à un agent est une décision de gouvernance, pas une décision technique. Cette section montre comment garder un agent utile sans le laisser agir au-delà de son mandat : placer les opérations sur le spectre d'autonomie, décider où situer les points d'approbation, nommer les couches de garde-fous qui entourent chaque action, et déterminer ce qui doit rester sous supervision humaine. Les exemples proviennent de la plateforme OPCP-EXPLORER, dont les agents virtuels — un agent Développeur qui modifie le code et un agent Opérations qui exécute START, STOP, RESTART, PS et LOGS — agissent sur de vrais déploiements.

Le spectre d'autonomie

L'autonomie est un spectre, pas un interrupteur. Chaque pas vers la droite accorde plus de liberté et retire un point de contrôle humain ; chaque pas doit donc être mérité par un risque plus faible ou des garde-fous plus solides.

  1. Suggérer — l'agent propose ; un humain réalise chaque action.
  2. Confirmer chaque étape — l'agent agit, mais un humain approuve avant chaque action. Les START/STOP qui affectent la facturation entrent ici.
  3. Agir avec points de contrôle — l'agent exécute plusieurs étapes en s'arrêtant à des points de contrôle définis (déployer automatiquement en préproduction, s'arrêter avant la production).
  4. Agir et rendre compte — l'agent achève la tâche puis en rend compte ; un humain peut intervenir ou revenir en arrière.
  5. Entièrement autonome — l'agent agit sans relecture dans le périmètre qui lui est accordé.

Points d'approbation

Un point d'approbation est un endroit où une action est suspendue jusqu'à ce qu'un humain donne son accord. Placez un point d'approbation partout où une action est difficile à annuler, coûte de l'argent ou élargit les accès : actions destructrices réservées à l'administrateur (supprimer une application, détruire une instance GPU/MIG), opérations affectant la facturation (START/STOP) et promotion en production.

Les couches de garde-fous

Les garde-fous contraignent chaque action, qu'un humain surveille ou non. Ils correspondent directement aux fonctions de sécurité d'OPCP-EXPLORER.

CoucheCe qu'elle contraintSur OPCP-EXPLORER
PermissionsQuelles actions sont autoriséesIsolation des utilisateurs avec des répertoires de déploiement séparés ; points de terminaison destructeurs réservés à l'administrateur
ValidationLa forme et la sûreté des entréesValidation des entrées, prévention des injections SQL, protection contre la traversée de répertoires
Limites / délaisCombien de temps et jusqu'où une action s'exécuteDélai d'opération de 30 minutes avec terminaison du groupe de processus ; tâches serverless en lecture seule et sans réseau
ObservabilitéQue chaque action soit auditableJournaux d'invites et billing_activities.log
Coupe-circuitLa capacité de tout arrêter d'un coupTerminaison du groupe de processus et dégradation gracieuse

Supervision humaine

La supervision humaine (HITL, human-in-the-loop) est la politique selon laquelle certaines actions ne doivent pas se dérouler sans qu'une personne participe à la décision. Réservez la HITL obligatoire aux actions irréversibles, sensibles pour la sécurité ou coûteuses, et traitez la dégradation gracieuse (le repli vers un mode réduit et sûr) comme une mesure de sécurité par défaut.

Configuration de la compétence : AGENTS_CONTROL

Le pilotage des agents de la plateforme est assuré par la compétence d'agent AGENTS_CONTROL, qui découvre, classe, inspecte et gère (arrêt/redémarrage/démarrage) les conteneurs d'agents en cours d'exécution sur les serveurs gérés.

Voir l'invite de la compétence AGENTS_CONTROL (SKILL.md) 
name: AGENTS_CONTROL
description: Control the AI agents run by the agentic-ai-plateform control plane —
discover, classify, inspect, and manage (stop/restart) the agent containers
running across the platform's managed servers.

IMPORTANT:
- Discovery and classification are read-only and safe.
- Stop/restart/start actions mutate running agents — always confirm the target
  with the operator before executing a lifecycle action.
- PLATFORM_URL defaults to https://agentic-ai-plateform.com.

#### 1. Resolve configuration and authenticate (login -> session cookie).
#### 2. List and classify agents via GET /api/agent-control/containers (append ?live=1 for a fresh scan).
#### 3. Inspect a specific agent, including the classification_evidence that justified the label.
#### 4. Manage lifecycle over SSH (docker stop|restart|start) after confirming the target.
#### 5. Verify and report the agent's new state.

Classification threshold: score >= 0.5 -> probable_agent (src/runtime_monitor/agent_classifier.py).

Configuration de la compétence : STATUS_APP

Les vérifications d'état sont pilotées par la compétence d'agent STATUS_APP, qui inspecte l'état d'exécution d'une application, résout ses ports et rend compte de son état au format JSON.

Voir l'invite de la compétence STATUS_APP (SKILL.md) 
You are an autonomous IT Operater agent with access to execute shell commands on a Linux server.
Check the status of the application and return detailed information in JSON format.

#### 1. Resolve {{APPLICATION_FOLDER}}, {{USER_NAME}}, {{NAME_OF_APPLICATION}}, {{USER_ID}}
# from ~/deployments//; fetch USER_ID via the platform API if unset.
#### 2. Calculate HTTP Ports (same logic as START_APP).
#### 3. Check the status via docker container ls, matching ${NAME_OF_APPLICATION}-.*-${USER_ID}-.*
# -> docker_status = IS_RUNNING | IS_NOT_RUNNING, and collect the published ports.
#### 4. Get git remotes for the application.
#### 5. Output a JSON object with environment_vars, docker_compose_ps, docker_ports, and git_remotes.

Points clés à retenir

  • L'installation, l'enregistrement, le démarrage, l'arrêt, la sauvegarde/restauration, la modification et la gouvernance des agents forment un cycle d'exploitation continu sur OPCP-EXPLORER.
  • Chaque opération est automatisée par une compétence d'agent nommée (START_APP, STOP_APP, BACKUP_DATABASE, RESTORE_DATABASE, CLEAN_DATABASE, MODIFY_CODE/KILL, AGENTS_CONTROL, STATUS_APP) dotée d'une invite fixe et auditable.
  • Les actions mutantes — démarrer, arrêter, tuer, nettoyer, piloter le cycle de vie — exigent une confirmation et se trouvent derrière des points d'approbation ; les actions destructrices restent sous supervision humaine.
  • Les garde-fous (permissions, validation, limites/délais, observabilité, coupe-circuit) entourent chaque action quel que soit le niveau d'autonomie.
