Lab: The shai Multi-Agent Orchestrator

Sandbox · Orchestration ⏱ ~40 min

This guided lab introduces shai, the multi-agent orchestrator that drives work across the opcp-explorer agentic-ai-platform. You will learn how the orchestrator is put together, what each agent role is responsible for, how a task is delegated from the orchestrator down to a worker agent, and how to drive the whole thing from the command line. Every command and configuration snippet on this page is illustrative text only — read it to understand the shape of the system; this lesson ships no runnable scripts.

Read-only lab: the examples below show the commands and configuration you would use on a live platform. Nothing here executes. Treat the snippets as a reference you adapt in your own environment, where the five guardrail layers apply.

Learning Objectives

  • Describe the architecture of the shai multi-agent orchestrator and how its parts fit together.
  • Name the agent roles — orchestrator, worker, and reviewer — and what each is responsible for.
  • Explain the delegation model: how a task flows from the orchestrator to a worker and back.
  • Follow step-by-step shai CLI instructions to configure, launch, and observe an orchestrated run.
  • Read an example orchestrator configuration and understand each field as a governance decision.

Orchestrator Architecture

shai is not a single agent — it is an orchestrator that coordinates several specialized agents toward one goal. The orchestrator owns the top-level task, breaks it into sub-tasks, hands each sub-task to a worker agent, collects the results, and decides when the overall job is done. Workers never talk to each other directly; everything flows through the orchestrator, which keeps the run observable and gives you a single point of control.

flowchart TD
    U[Operator / CLI] --> O[shai orchestrator]
    O --> W1[Worker agent: discovery]
    O --> W2[Worker agent: action]
    O --> R[Reviewer agent]
    W1 --> O
    W2 --> O
    R --> O
    O --> U

The orchestrator is the hub: it delegates to workers, routes results through a reviewer, and reports back to the operator.

Three things make this a defensible design rather than just a fan-out:

  • A single coordinator. One orchestrator holds the plan, so there is exactly one place that decides what runs next and when to stop.
  • Isolated workers. Each worker gets a narrow task and a scoped set of tools, so a mistake in one worker cannot cascade into another.
  • A review gate. Mutating results pass through a reviewer before the orchestrator accepts them, keeping a human-aligned check in the loop.

Agent Roles

A shai run is made up of three kinds of agent. Each has one job and a permission scope sized to that job.

RoleResponsibilityTypical tool scope
OrchestratorOwns the top-level goal, plans and sequences sub-tasks, delegates to workers, aggregates results, decides when to stop.No host tools; delegation only
WorkerExecutes one delegated sub-task (discover, start, stop, back up, modify) and returns a structured result.Scoped read / write / bash as the task requires
ReviewerInspects a worker's proposed mutating action and approves or rejects it before the orchestrator applies it.read only
Governance: the orchestrator deliberately holds no host tools. It can only delegate. Powerful grants like write and bash live on individual workers and are scoped per sub-task, so the blast radius of any one agent stays small.

The Delegation Model

Delegation is the heart of shai. The operator hands the orchestrator a goal; the orchestrator decides which worker should handle each piece and passes a self-contained task down. A delegated task carries everything the worker needs and nothing it does not:

  • A goal statement — the one thing this worker must accomplish.
  • Scoped inputs — only the data relevant to the sub-task.
  • A tool grant — the minimal set of tools for that sub-task.
  • A return contract — the structured result the orchestrator expects back.

The lifecycle of a single delegated task looks like this:

sequenceDiagram
    Operator->>Orchestrator: goal
    Orchestrator->>Worker: delegate(sub-task, scoped tools)
    Worker->>Worker: run sub-task
    Worker-->>Orchestrator: structured result
    Orchestrator->>Reviewer: review(result) if mutating
    Reviewer-->>Orchestrator: approve / reject
    Orchestrator-->>Operator: aggregated outcome

A read-only sub-task returns straight to the orchestrator; a mutating one is routed through the reviewer first.

Because the orchestrator is the only agent that sees the whole plan, it is also the only place that enforces operational limits — maximum sub-tasks, retry ceilings, and a wall-clock timeout for the run. Those limits are the orchestrator-level form of the stopping criteria you met earlier in the course.

Step-by-Step: Driving shai from the CLI

The commands below walk through one orchestrated run end to end. They are illustrative — adapt the paths and names to your own environment.

Step 1 — Check the orchestrator is available

Confirm the CLI is on your path and reports a version before you do anything else.

shai --version
shai orchestrator status

Step 2 — Point shai at an orchestrator configuration

The orchestrator is defined by one config file (shown in full in the next section). Validate it before you launch so a typo fails loudly rather than mid-run.

shai orchestrator validate --config ./orchestrator.config.json

Step 3 — Launch a run with a goal

Hand the orchestrator a single top-level goal. The orchestrator plans the sub-tasks and delegates them to workers itself — you do not call the workers directly.

shai orchestrator run \
  --config ./orchestrator.config.json \
  --goal "Discover running containers and report probable agents" \
  --max-subtasks 6

Step 4 — Watch delegation in real time

Follow the run so you can see each sub-task delegated, each worker result returned, and each review decision as it happens.

shai orchestrator logs --follow --run-id latest

Step 5 — Read the aggregated outcome

When the orchestrator decides the goal is met (or a limit is hit), it prints one aggregated report combining every worker result.

shai orchestrator report --run-id latest

Step 6 — Stop a run if needed

The kill switch halts the orchestrator and every worker it delegated to, in one command.

shai orchestrator stop --run-id latest
Governance: stop is your single reliable kill switch. Because workers only ever run under the orchestrator, stopping the orchestrator tears down the whole run — there are no orphaned workers to chase down separately.

Example Orchestrator Configuration

The orchestrator is defined entirely by one JSON file. It names the orchestrator, picks the model that plans for it, declares the worker and reviewer agents it may delegate to, and sets the operational limits for a run. Here is the full illustrative file, which we then open field by field.

{
  "name": "opcp-explorer-orchestrator",
  "description": "shai multi-agent orchestrator that plans a goal, delegates sub-tasks to scoped workers, and routes mutating actions through a reviewer.",
  "llm_provider": {
    "provider": "ovhcloud",
    "model": "Qwen3.5-397B-A17B",
    "mode": "FunctionCall"
  },
  "orchestrator": {
    "max_subtasks": 6,
    "max_retries_per_subtask": 2,
    "run_timeout_seconds": 600,
    "require_review_for_mutating": true
  },
  "agents": {
    "discovery-worker": {
      "role": "worker",
      "system_prompt": "Discover the containers on the platform and return a structured list.",
      "tools": ["read", "bash"]
    },
    "action-worker": {
      "role": "worker",
      "system_prompt": "Apply the single action delegated to you and return the result.",
      "tools": ["read", "write", "bash"]
    },
    "reviewer": {
      "role": "reviewer",
      "system_prompt": "Inspect the proposed mutating action and approve or reject it.",
      "tools": ["read"]
    }
  }
}

Identity: name and description

The name labels the orchestrator in logs and audit trails; description states what it coordinates in one human-readable sentence. A stable name is what lets a reviewer trace a run back to the configuration that authorized it.

llm_provider

The llm_provider block picks the model that plans for the orchestrator — provider ovhcloud, model Qwen3.5-397B-A17B, mode FunctionCall. In FunctionCall mode the orchestrator can issue delegation calls to its worker agents rather than only emitting text.

The orchestrator limits block

This block is the orchestrator-level stopping criteria. max_subtasks caps how many pieces a goal can be split into; max_retries_per_subtask bounds how often a failed sub-task is retried; run_timeout_seconds sets a wall-clock ceiling for the whole run; and require_review_for_mutating forces every mutating worker result through the reviewer before the orchestrator applies it.

Governance: require_review_for_mutating: true is the review gate from the architecture diagram made concrete. Leaving it on keeps a check between a worker proposing a change and that change taking effect — do not turn it off for anything that writes, starts, stops, or deletes.

The agents map

Each entry names an agent the orchestrator may delegate to, declares its role (worker or reviewer), gives it a one-line system_prompt scoping its job, and grants it a minimal tools set. Note the pattern: the discovery worker is read-mostly (read, bash), the action worker is the only one granted write, and the reviewer is read-only by design.

Governance: the tool grants here are least privilege in action. Only the action-worker can change the platform, and even its changes must clear the reviewer. If a sub-task does not need write or bash, do not grant them to the agent that runs it.

Key Takeaways

  • shai is an orchestrator that coordinates specialized agents toward one goal — not a single agent.
  • Three roles: an orchestrator that plans and delegates, workers that execute scoped sub-tasks, and a reviewer that gates mutating actions.
  • Delegation carries a goal, scoped inputs, a minimal tool grant, and a return contract — nothing more.
  • You drive a run from the CLI: validate the config, launch with a goal, follow the logs, read the report, and stop with the kill switch.
  • Operational limits and the review gate live in the orchestrator config, making the whole run observable and bounded.
