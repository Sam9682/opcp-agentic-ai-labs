Lab: CLI Agent Orchestrator (CAO) Supervisor Loop

Sandbox · Orchestration ⏱ ~40 min

This hands-on lab drives the CLI Agent Orchestrator (CAO) — a real tool you install and run yourself. CAO coordinates several provider CLIs as a team: a supervisor agent breaks a goal into sub-tasks and delegates them to scoped worker agents. Over the course of the lab you install CAO, start the cao-server, launch a supervisor in your own project directory, delegate a small task, watch the run through the attached terminal and the Web UI, and shut everything down. The commands on this page are real and executable against your own CAO installation.

Learning Objectives

  • Describe how CAO is put together: a local cao-server that starts provider CLIs in isolated terminal sessions.
  • Name the agent roles — supervisor, worker, and reviewer — and what each is responsible for.
  • Explain the delegation model: how a task flows from the supervisor to a worker and back.
  • Run the core supervisor loop from the command line: install, launch, delegate, observe, and shut down.
  • Read an example CAO agent profile and understand each field as a governance decision.

Prerequisites & Setup

Before you run anything, make sure your machine has the tools CAO depends on. Install each of these and confirm it is on your path:

  • Python 3.11+ — CAO runs on Python 3.11 or later.
  • tmux 3.3+ — CAO starts each provider CLI in an isolated tmux terminal session, so you need tmux 3.3 or later.
  • uv — the Python package and tool installer used to install the cao command line tool.
  • At least one authenticated provider CLI — each agent is backed by a provider CLI with its own native authentication. The default provider is the Kiro CLI; make sure it is installed and signed in before you launch an agent.

CAO Architecture

CAO is not a single agent — it is a local orchestration layer. The cao-server process runs on your machine and starts each provider CLI inside its own isolated tmux terminal session, so every agent is a full CLI process with its own native authentication rather than a hidden sub-process. On top of that, a supervisor profile owns the top-level goal, breaks it into sub-tasks, and delegates each one to a specialist worker agent — either in parallel when the sub-tasks are independent or in sequence when they depend on one another. Workers never talk to each other directly; everything flows through the supervisor, which keeps the run observable and gives you a single point of control.

flowchart TD
    U[Operator / CLI] --> S[CAO supervisor]
    S --> W1[Worker agent: developer]
    S --> W2[Worker agent: developer]
    S --> R[Reviewer agent]
    W1 --> S
    W2 --> S
    R --> S
    S --> U

The supervisor is the hub: it delegates to worker agents, routes results through a reviewer, and reports back to the operator.

Three things make this a defensible design rather than just a fan-out:

  • A single coordinator. One supervisor holds the plan, so there is exactly one place that decides what runs next and when to stop.
  • Isolated workers. Each worker runs as its own provider CLI process in an isolated terminal session with an allowedTools scope sized to its task, so a mistake in one worker cannot cascade into another.
  • A review gate. Mutating work passes through a role: reviewer agent before the supervisor accepts it, keeping a human-aligned check in the loop.

Agent Roles

A CAO run is made up of three kinds of agent, each backed by a built-in profile (code_supervisor.md, developer.md, reviewer.md). Each has one job and an allowedTools scope sized to that job.

Role (role:)ResponsibilityTypical tool scope
supervisor (code_supervisor)Owns the top-level goal, breaks it into sub-tasks, delegates each to a worker, routes mutating work through the reviewer, aggregates results, and decides when the job is done. Never writes code itself.Coordination only: @cao-mcp-server, fs_read, fs_list; delegates via delegateTools (defaults to ["*"])
worker — developer (developer)Executes one delegated, self-contained sub-task — implements the scoped change — and returns a structured result to the supervisor.Read/write/run: fs_*, execute_bash, @cao-mcp-server (@builtin), scoped per sub-task
worker — reviewer (reviewer)Inspects a worker's proposed mutating action for correctness, quality, and safety, then approves or rejects it before the supervisor accepts the change.Read-only: fs_read, fs_list, @cao-mcp-server (@builtin)
Governance: the supervisor deliberately holds no host write or run tools — it coordinates and delegates. Powerful grants like fs_write and execute_bash live on the developer worker and are scoped per sub-task through allowedTools, while delegateTools caps what the supervisor may hand down, so the blast radius of any one agent stays small.

The Delegation Model

Delegation is the heart of CAO. The operator hands the supervisor a goal; the supervisor decides which worker should handle each piece and delegates a self-contained sub-task down. A delegated sub-task carries everything the worker needs and nothing it does not:

  • A goal statement — the one thing this worker must accomplish.
  • Scoped inputs — only the data relevant to the sub-task.
  • A tool grant — the minimal set of tools for that sub-task, bounded by the supervisor's delegateTools ceiling.
  • A return contract — the structured result the supervisor expects back.

A worker runs its sub-task and returns a structured result to the supervisor. When the work is mutating — it changes files or state — the supervisor routes that result through a reviewer agent before accepting it; a read-only sub-task returns straight to the supervisor. The lifecycle of a single delegated task looks like this:

sequenceDiagram
    Operator->>Supervisor: goal
    Supervisor->>Worker: delegate(sub-task, scoped tools)
    Worker->>Worker: run sub-task
    Worker-->>Supervisor: structured result
    Supervisor->>Reviewer: review(result) if mutating
    Reviewer-->>Supervisor: approve / reject
    Supervisor-->>Operator: aggregated outcome

A read-only sub-task returns straight to the supervisor; a mutating one is routed through the reviewer first.

Because the supervisor is the only agent that sees the whole plan, it is also the only place that enforces operational limits — it sequences sub-tasks, retries failed delegations, and decides when the goal is met or a limit is hit. Those supervisor-loop controls are the orchestration-level form of the stopping criteria you met earlier in the course.

Step-by-Step: Core Supervisor Loop

The steps below walk through one supervisor loop end to end against your own project. Run every command yourself: install CAO, start the server, launch a supervisor from your project directory, delegate a small task, watch it run, and shut it down. Wherever you see /path/to/your/project, substitute the absolute path to the project you want the supervisor to work in.

Step 1 — Install CAO and verify

Install the cao command line tool with uv, then confirm it is on your path by printing its help.

uv tool install git+https://github.com/Sam9682/cli-agent-orchestrator.git@main --upgrade
cao --help

Step 2 — Install the supervisor agent

Install the built-in supervisor profile so cao launch can start it.

cao install code_supervisor

Step 3 — Start the server (Terminal A)

In a dedicated terminal, start cao-server. This is a long-running process that starts each provider CLI in its own isolated tmux terminal session — leave it running for the rest of the lab.

cao-server

Step 4 — Launch the supervisor (Terminal B)

In a separate terminal, change into your project directory and launch the supervisor. This attaches you to the supervisor's session so you can talk to it directly.

cd /path/to/your/project && cao launch --agents code_supervisor

Step 5 — Delegate a small task

In the attached supervisor session, type a short goal — keep it small and reviewable, for example asking the supervisor to make one small, well-scoped change to your project. The supervisor breaks the goal into sub-tasks and delegates them to a worker agent; you do not call the worker directly.

Step 6 — Observe the run

Watch the delegation happen in two places: the attached launch terminal shows the supervisor and worker activity as it unfolds, and the Web UI at http://localhost:9889 gives you a visual view of the sessions and the delegation between them.

Step 7 — Shut down

When you are done, shut the run down. Stop a single named session, or tear down every session at once.

cao shutdown --session {session-name}
cao shutdown --all
Governance: cao shutdown is your kill switch. cao shutdown --session {session-name} stops one session; cao shutdown --all tears down every session CAO is running. Because workers only run under the supervisor's session, shutting down stops the supervisor and its workers together — there are no orphaned agents to chase down separately.

Example CAO Agent Profiles

A CAO agent is not a JSON blob — it is a Markdown file with a YAML frontmatter header and a Markdown body. The frontmatter declares the agent's identity and its governance envelope (who it is, what provider backs it, which tools it may use, and how much it may hand down to workers); the body is the system prompt that tells the agent how to behave. Here are two real profiles — a supervisor and a developer worker — which we then open field by field.

Supervisor profile (code_supervisor.md)

---
name: code_supervisor
description: Coding Supervisor Agent in a multi-agent system
role: supervisor
provider: kiro_cli
delegateTools: ["*"]
---

You are the Coding Supervisor. You never write code yourself. You break a
goal into sub-tasks, delegate each to a worker agent, route mutating work
through the reviewer, and decide when the job is done.

Worker profile (developer.md)

---
name: developer
description: Developer Agent in a multi-agent system
role: developer
provider: kiro_cli
allowedTools: ["fs_read", "fs_write", "execute_bash", "@cao-mcp-server"]
---

You are a Developer agent. Implement the single scoped sub-task delegated to
you and return a structured result.

name

Governance decision: the name is the agent's stable identifier — it is how the profile shows up in logs and audit trails, and it is the handle you pass to cao install and to cao launch --agents. A stable, meaningful name is what lets a reviewer trace a run back to the exact profile that authorized it.

role

Governance decision: the role is a named permission preset — allowed values are supervisor, developer, and reviewer. Choosing a role is choosing a default allowedTools bundle: a supervisor coordinates and delegates, a developer gets read/write/execute to do scoped work, and a reviewer is read-only by design. The role is the coarse-grained governance control you set before you tune anything else.

provider

Governance decision: provider picks which authenticated provider CLI backs the agent — here kiro_cli, the default Kiro CLI. Because agents remain full CLI processes with native authentication, the provider you name is the identity and credentials the agent's actions run under, so it belongs in the audit story alongside the tool grants.

allowedTools

Governance decision: allowedTools is the explicit tool allowlist for the agent itself, and it overrides the role's defaults. It is the concrete expression of least privilege: the developer above is granted exactly fs_read, fs_write, execute_bash, and the @cao-mcp-server tools — nothing more. If a sub-task does not need to write files or run commands, do not list those tools in the profile that runs it.

Governance: the role sets a sensible default, but allowedTools is where you make least privilege explicit. Narrow the list to exactly what the agent needs; an allowlist you can read at a glance is an allowlist a reviewer can approve.

delegateTools

Governance decision: delegateTools is the delegation ceiling — the most an agent may grant to the workers it creates, never more than this regardless of what a worker's own profile asks for. It defaults to ["*"] for role: supervisor (a supervisor may hand down any tool it is itself allowed) and to the agent's own allowedTools for every other role. The supervisor above keeps the explicit delegateTools: ["*"]; the developer worker does not set one, so its ceiling is simply its own allowedTools.

Governance: delegateTools is how you cap blast radius across a whole delegation tree. Lowering a supervisor's delegateTools below ["*"] guarantees that no worker it spawns can exceed that bound — the ceiling is enforced on delegation, not on trust. A reviewer-role agent (from reviewer.md, read-only allowedTools) is what the supervisor routes mutating work through before accepting it.

Governance Mapping

The governance vocabulary from earlier in the course is not abstract here — each concept maps onto a concrete CAO mechanism you have already seen in this lab.

  • Least privilege → allowedTools / delegateTools. allowedTools sizes each agent's own tool grant down to exactly what its task needs, and delegateTools caps the most a supervisor may hand down to the workers it creates. Together they keep every agent's blast radius as small as the work allows.
  • Review gate → a role: reviewer agent. Mutating work is routed through a CAO reviewer-role agent (from reviewer.md, read-only allowedTools) that inspects the change before the supervisor accepts it, keeping a human-aligned check in the loop.
  • Kill switch → cao shutdown. cao shutdown --session {session-name} stops one named session and cao shutdown --all tears down every session CAO is running — a single, decisive way to halt a run.
  • Operational limits → supervisor-loop controls. The supervisor is the single coordinator that sequences sub-tasks, retries failed delegations, and decides when the goal is met or a limit is hit; tool restrictions bound each worker's blast radius. Those are the real, enforced limits of a CAO run.

Key Takeaways

  • CAO coordinates several provider CLIs as a team through a supervisor — it is an orchestration layer, not a single agent.
  • Three roles: a supervisor that plans and delegates, a worker (developer) that executes scoped sub-tasks, and a reviewer that gates mutating work.
  • A delegation carries a goal, scoped inputs, a minimal tool grant (bounded by delegateTools), and a return contract — nothing more.
  • You drive the core supervisor loop from the CLI: install CAO, start cao-server, launch the supervisor, delegate a small task, observe the run, and shut it down.
  • Governance is concrete: least privilege lives in allowedTools/delegateTools, the review gate is a reviewer-role agent, and cao shutdown is the kill switch.
