Configuring a SHAI Agent with MCP to OPCP-EXPLORER

Afternoon · Governance ⏱ ~45 min

This lesson walks you through configuring a SHAI agent whose single stdio MCP (Model Context Protocol) connection reaches the opcp-explorer agentic-ai-platform. You will open the AGENTS_CONTROL_AGENT_NO_SKILL.config.json file field by field, wire the MCP server block that points at the platform, run one container-discovery prompt, and read the live Container Discovery Results report the agent returns. The goal is to leave you able to reproduce the MCP connection yourself and to interpret — and govern — what the discovery report tells you.

Learning Objectives

  • Configure a SHAI agent from the AGENTS_CONTROL_AGENT_NO_SKILL.config.json file, field by field.
  • Wire the stdio MCP server block that connects the agent to the opcp-explorer agentic-ai-platform.
  • Run the single discovery prompt that triggers a live container scan.
  • Interpret the classification report the agent returns.
  • Apply governance to every autonomy-granting choice in the configuration.

The AGENTS_CONTROL_AGENT_NO_SKILL.config.json file

The agent is defined entirely by one JSON file. It names the agent, picks the model that reasons for it, lists the built-in tools it may use, sets the one-line task it runs on launch, caps its generation, and wires its single MCP connection. Here is the full file, which we then open field by field.

{
  "name": "AGENTS_CONTROL_AGENT_NO_SKILL",
  "description": "SHAI agent that discovers and classifies the containers running on the opcp-explorer platform over a single MCP connection.",
  "llm_provider": {
    "provider": "ovhcloud",
    "model": "Qwen3.5-397B-A17B",
    "mode": "FunctionCall"
  },
  "tools": ["read", "write", "bash"],
  "system_prompt": "Call agent_control_containers with live=true and list the containers",
  "max_tokens": 8192,
  "temperature": 0.3,
  "compaction": {
    "enabled": true,
    "trigger_tokens": 6144,
    "keep_last_messages": 6
  },
  "verification": {
    "enabled": false
  },
  "mcp_servers": {
    "opcp-explorer": {
      "command": "/home/ubuntu/agentic-ai-plateform/.venv/bin/python",
      "args": ["/home/ubuntu/agentic-ai-plateform/src/mcp_interface.py"],
      "enabled_tools": ["*"],
      "required": false
    }
  }
}

Identity: name and description

The name field labels the agent in logs, dashboards, and audit trails; description states what it is for in one human-readable sentence. Naming is not cosmetic — when an agent acts on real deployments, a clear, stable name is what lets a reviewer trace an action back to the configuration that authorized it.

llm_provider

The llm_provider block picks the model that reasons for the agent: provider ovhcloud, model Qwen3.5-397B-A17B, and mode FunctionCall. FunctionCall mode lets the model invoke tools and MCP functions directly rather than only emitting text, which is what makes the discovery call possible.

Governance: choosing a model and provider is a policy decision, not just a technical one. Pinning inference to OVHcloud-hosted Qwen3.5-397B-A17B keeps reasoning on a known, accountable platform — part of the configuration you sign off on, not an afterthought.

Built-in tools: read, write, and bash

The tools array grants the agent three built-in capabilities: read inspects files, write creates or edits them, and bash runs shell commands on the host. Together they let the agent do real work rather than only talk about it.

Governance: write and bash are the two powerful grants here — one changes files, the other executes commands. Grant them only when the task needs them, scope what they can touch, and keep their activity observable so every change has a trail.

system_prompt

The system_prompt is the single standing instruction the agent runs on launch: Call agent_control_containers with live=true and list the containers. The live=true argument forces an on-demand scan of the platform rather than returning a cached result, so the report reflects the fleet as it is right now.

Generation limits: max_tokens (8192) and temperature (0.3)

max_tokens caps a single generation at 8192 tokens, bounding how much the agent can produce in one turn. temperature at 0.3 keeps output focused and repeatable — a low temperature suits an operations agent, where you want the same input to yield the same, predictable action rather than creative variation.

Compaction block

The compaction block keeps long sessions within the model's context window: once the conversation grows past trigger_tokens, older turns are summarized while the most recent messages (keep_last_messages) are kept verbatim. This lets the agent run multi-step work without losing the thread or overflowing the window.

Disabled verification

The verification block is set to enabled: false, so the agent's output is not run through an extra verification pass before it is returned.

Governance: turning verification off removes a safety check. It is a deliberate, accountable trade-off — acceptable for a read-only discovery task where speed matters, but something you record and revisit before the same agent is allowed to perform mutating operations.

Connecting to OPCP-EXPLORER over MCP

A single stdio MCP server connects the agent to the opcp-explorer platform. The platform runs as a local Python process that the agent launches and talks to over standard input/output — no network port, no separate service to manage. The block below is the entire connection.

"mcp_servers": {
  "opcp-explorer": {
    "command": "/home/ubuntu/agentic-ai-plateform/.venv/bin/python",
    "args": ["/home/ubuntu/agentic-ai-plateform/src/mcp_interface.py"],
    "enabled_tools": ["*"],
    "required": false
  }
}

The command points at the platform's virtual-environment Python interpreter, and args hands it the mcp_interface.py entry point; together they start the OPCP-EXPLORER MCP server as a child process. enabled_tools is ["*"] and required is false.

Governance: enabled_tools: ["*"] grants the agent every tool the server exposes, present and future — convenient, but the opposite of least privilege, so confirm the full tool surface is one you accept. required: false lets the agent start even when the server is down: handy for resilience, but it means a missing connection fails quietly rather than stopping the agent, so you must detect that case yourself.

Reading the Discovery Report

Once the agent launches, its system_prompt fires a single agent_control_containers call with live=true, and the OPCP-EXPLORER MCP server answers with a Container Discovery Results (Live Scan) report. The report walks the managed fleet, classifies every container it finds, and tells you which ones look like running agents. The rest of this lesson reads that report section by section.

Scan summary

The live scan reached 48 containers on opcp-psmc-platform (server_id 4) and reported them in full. It also recorded 1 scan error on server_id 5: the server could not be inspected because of an SSH authentication failure, so none of its containers appear in the results.

Governance: an unreachable server is a blind spot, not an empty one. The report is complete only for the servers that answered — server_id 5 returned nothing because the scan never authenticated, so treat its containers as unknown rather than absent until the SSH credential is fixed and the scan re-run.

Classification breakdown

Across the 48 scanned containers the classifier returned 4 as probable_agent (confidence 0.60–1.00) and 44 as unclassified (confidence 0.00–0.40). The classifier is a pure, explainable heuristic — a container scores probable_agent once its evidence crosses the threshold (score >= 0.5), and every point in the score has a named reason you can audit.

Probable agents

These are the four containers the scan flagged as probable agents, from the strongest signal to the weakest. The names and confidence scores come straight from the report; the evidence column summarizes why each one crossed the threshold.

The top row is a textbook agent: a SHAI web-interface image whose runtime shows agent tokens and outbound LLM traffic scores a perfect 1.00. The datastore row (0.65) is interesting — it is not an agent itself, but the classifier flags it because it is part of the SHAI stack, a supporting service rather than a standalone agent. The two opcp-agentic-ai-labs rows (0.75 and 0.60) sit lower: the app container carries agent-related tokens, while the base image is a weaker, more ambiguous signal just over the line.

Notable findings and recommendations

Reading the report as a whole, a few things stand out:

  • The highest-confidence agent is the SHAI web interface (ai-shai-web-interface-app-25-8529, 1.00) — the expected centerpiece of the stack.
  • The remaining 44 containers are unclassified, consistent with ordinary infrastructure (databases, proxies, workers) rather than agents.
  • server_id 5 could not be scanned at all, so its agent posture is unknown.

From those findings, the recommended follow-up is:

  • Investigate and repair the SSH credential for server_id 5, then re-run the scan with live=true so the fleet view is complete.
  • Confirm the four probable agents are expected, and that the 0.65 datastore flag is understood as a supporting service rather than a rogue agent.
  • Spot-check a sample of the unclassified containers to make sure none is a low-signal agent sitting just under the threshold.
Governance: discovery and classification are read-only — the agent inspects and reports, so running it is safe. The follow-up is where risk enters: any stop, restart, or start acts on live containers and can take an agent — or a service — down. Keep a human in the loop for every such action, in line with the afternoon lessons on Human-in-the-Loop & OVHcloud AI Policy and Guardrails: Five Layers.
