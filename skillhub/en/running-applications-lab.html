Lab: OPCP-EXPLORER Running Applications

Sandbox Labs · Beginner ⏱ ~90 min

This single hands-on lab consolidates the full OPCP-EXPLORER operations workflow that was previously spread across seven separate sandbox lessons. You will install the Agentic-AI-Platform on bare-metal Ubuntu, register and start applications, stop them gracefully, back up and restore their databases, modify them with AI assistance, and govern the agents that drive every one of those actions. Each section below maps to one former topic, so nothing from the original material is lost — it is simply organized as one coherent lab.

How to use this lab: work through the sections in order the first time. Each section states its prerequisites, what you will learn, the concrete commands, and the agent skill that automates the action. All example commands and skill prompts are illustrative — read them to understand what the agent runs on your behalf.

1. Installation on Bare-Metal Ubuntu

Deploy the Agentic-AI-Platform on a fresh bare-metal Ubuntu server (22.04 or 24.04 LTS), from system preparation to final deployment.

Prerequisites

  • A clean Ubuntu 22.04 or 24.04 LTS installation
  • Root or sudo access
  • At least 4 GB RAM and 20 GB disk space
  • Internet connectivity for package downloads
  • An NVIDIA-compatible GPU (optional, for MIG support)

Quick Installation

The fastest way to deploy the platform is the automated init_pltf.sh script, which runs every step for you and sets up the control plane for the Agentic AI platform. The script lives at the root of the dedicated platform repository on GitHub: github.com/Sam9682/agentic-ai-plateform.

git clone https://github.com/Sam9682/agentic-ai-plateform.git
cd agentic-ai-plateform
# init_pltf.sh is here, in the repository root:
ls -l init_pltf.sh
chmod +x init_pltf.sh
./init_pltf.sh
Note: Run the script from the repository root, always with the ./ prefix. It prompts for the platform identity (folder slug, display name, repo URL) and writes PLTF_NAME / PLTF_FOLDER into conf/deploy.ini. Press Enter to accept the defaults, or pre-set them via environment variables for a non-interactive run.
Manual Installation (optional)

These are the individual steps the automated script performs. Follow them only if you want a step-by-step install or need to customize the process.

Step 1: Install System Dependencies

sudo apt update
sudo apt --fix-broken install -y
sudo apt install -y python3 python3-pip python3-venv net-tools unzip

Step 2: Install CLI Tools (shai and Terraform)

# OVH CLI (shai)
curl -fsSL https://raw.githubusercontent.com/ovh/shai/main/install.sh | sh
echo 'export PATH="~/.local/bin:$PATH"' >> ~/.bashrc

# Terraform
curl -s "https://releases.hashicorp.com/terraform/1.14.5/terraform_1.14.5_linux_amd64.zip" -o "terraform.zip"
unzip -q terraform.zip
sudo mv terraform /usr/local/bin/
rm -f terraform.zip

Step 3: Network Configuration (Netplan)

The script configures interface priorities so the public interface is preferred for default routing: public interface route metric 50 (high priority), private interface route metric 200 (low priority). Interface detection is automatic (private ranges 10.x, 172.16-31.x, 192.168.x).

Warning: A backup of the existing netplan file is created automatically before any modification.

Step 4: Install Docker

curl -fsSL https://get.docker.com -o get-docker.sh
sudo sh get-docker.sh
sudo usermod -aG docker $USER
sudo curl -sL "https://github.com/docker/compose/releases/latest/download/docker-compose-$(uname -s)-$(uname -m)" -o /usr/local/bin/docker-compose
sudo chmod +x /usr/local/bin/docker-compose
rm -f get-docker.sh
Note: Log out and back in for the docker group membership to take effect.

Step 5: Install NVIDIA Drivers and GPU Support (Optional)

sudo apt install -y nvidia-driver-550 nvidia-utils-550
sudo nvidia-smi -mig 1
sudo apt install -y nvidia-container-toolkit
docker run --rm --gpus '"device=0"' nvidia/cuda:12.3.0-base-ubuntu22.04 nvidia-smi
Note: MIG mode is only available on NVIDIA A100, A30, H100, and similar GPUs; it is skipped on incompatible hardware.

Step 6: Configure AWS (OVH S3 Storage)

mkdir -p ~/.aws
cat > ~/.aws/config <<EOF
[profile OVH-SWAUTOMORPH]
region = gra
output = json
EOF
cat > ~/.aws/credentials <<EOF
[OVH-SWAUTOMORPH]
aws_access_key_id = YOUR_ACCESS_KEY
aws_secret_access_key = YOUR_SECRET_KEY
endpoint_url = https://s3.gra.io.cloud.ovh.net/
signature_version = s3v4
EOF
export AWS_DEFAULT_PROFILE=OVH-SWAUTOMORPH
export AWS_ENDPOINT_URL_S3=https://s3.gra.io.cloud.ovh.net/

Step 7: Clone the Repository

git clone https://github.com/Sam9682/opcp-agentic-ai-labs.git
cd opcp-agentic-ai-labs
git submodule update --init --recursive

Step 8: Set Up the Python Environment

python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

Step 9: Final Configuration

mkdir -p logs
chmod +x setup_modsecurity_config.sh
cd ~
mkdir -p deployments/admin
Post-installation checklist — do not forget to:
  • Modify ./conf/deploy.ini with your platform settings, especially PLTF_NAME and DOMAIN
  • Add the SSL certificate to ~/opcp-agentic-ai-labs/ssl/fullchain_domain.crt and the private key to ~/opcp-agentic-ai-labs/ssl/privateKey_domain.key for nginx HTTPS
  • Enter aws_access_key_id and aws_secret_access_key in ~/.aws/credentials for S3 synchronization

2. Adding New Applications

Register and deploy applications on the platform using the CLI, the REST API, or the web admin interface. The web admin exposes an Applications Management table listing every registered application with its ID, name, URL, description, Git URL, repo size, and build/start/stop/ps timings, plus Edit and Delete actions.

Method 1: Web Interface

  1. Log into the admin interface
  2. Open the Applications menu in the top navigation bar
  3. Click Add New Application
  4. Fill in the form: Name (technical, no spaces, lowercase), Description, URL, and Git URL
  5. Submit the form

Method 2: CLI

cd ~/opcp-agentic-ai-labs
source .venv/bin/activate
python opcp-explorer.py add-app \
  --name "my-application" \
  --description "My application description" \
  --git-url "git@github.com/user/my-application.git" \
  --url "https://my-domain.com/admin/my-application"

Method 3: REST API

curl -X POST https://<your-domain>/api/applications \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer <your-token>" \
  -d '{
    "name": "my-application",
    "description": "My application description",
    "git_url": "git@github.com/user/my-application.git",
    "url": "https://my-domain.com/admin/my-application"
  }'
Warning: Deleting an application is irreversible. Make sure you have a backup before proceeding.

3. Starting Applications

Start a registered application, understand its Docker container orchestration, monitor startup logs, and verify its health.

# Navigate to the platform directory

# Start an application

Skill configuration: START_APP

Starting an application is driven by the START_APP agent skill. The prompt below is the exact configuration the agent follows to deploy and start an application. Tokens such as {{APPLICATION_FOLDER}} and {{USER_ID}} are substituted with concrete values at runtime.

View the START_APP skill prompt (SKILL.md) 
You are an autonomous IT Operater agent with access to execute shell commands on a Linux server.
Please deploy and start the application by executing the following steps in sequence.
IMPORTANT :
- all commands have to be executed in the application located {{APPLICATION_FOLDER}}.
- Execute all steps to deploy with the environment variable USER_ID={{USER_ID}}

#### 1. Check Prerequisites (docker and docker-compose must be installed):
command -v docker || exit 1
command -v docker-compose || exit 1

#### 2. Calculate HTTP Ports used by the application's containers:
source {{APPLICATION_FOLDER}}/conf/deploy.ini
RANGE_START=${RANGE_START:-6000}
RANGE_RESERVED=${RANGE_RESERVED:-100}
RANGE_PORTS_PER_APPLICATION=${RANGE_PORTS_PER_APPLICATION:-12}
if ! [[ "$USER_ID" =~ ^[0-9]+$ ]]; then USER_ID=0; fi
PORT_RANGE_BEGIN=$((RANGE_START + USER_ID * RANGE_RESERVED))
base=$((PORT_RANGE_BEGIN + APPLICATION_IDENTITY_NUMBER * RANGE_PORTS_PER_APPLICATION))

#### 3. Generate Secrets (only if .env.prod doesn't exist), build .env.prod with
# POSTGRES_* credentials, DATABASE_URL, JWT_SECRET, DOMAIN and API_URL, then chmod 600 .env.prod

#### 4. Generate Nginx Configuration from conf/nginx.conf.template if it exists.

#### 5. Start the docker services:
docker-compose -p "$NAME_OF_APPLICATION-$USER_ID-$HTTPS_PORT" -f docker-compose.yml --env-file .env.prod up -d

#### 6. Configure Firewall (UFW) to allow the calculated HTTP/HTTPS ports.

#### 7. Verify the service is up:
curl -f -s "https://${DOMAIN}:${HTTPS_PORT}/" || true

Finally, display the link to the web site: https://${DOMAIN}:${HTTPS_PORT}

4. Stopping Applications

Gracefully stop an application, understand the shutdown process, and clean up resources afterwards.

# Stop a specific application
cd ~/deployments/<app_name>
docker-compose down

# Stop with volume cleanup (removes data)
docker-compose down -v

# Stop the entire platform
cd ~/opcp-agentic-ai-labs
docker-compose down
Warning: The -v flag removes associated volumes and data. Always create a backup before using it.

Skill configuration: STOP_APP

Stopping an application is driven by the STOP_APP agent skill, which performs a graceful shutdown of the application's running Docker containers.

View the STOP_APP skill prompt (SKILL.md) 
Please stop all running Docker containers for the specified user instance.
IMPORTANT :
- all commands have to be executed in the application located {{APPLICATION_FOLDER}}.
- Execute all steps with the environment variable USER_ID={{USER_ID}}

#### 1. Calculate HTTP Ports (same port-calculation logic as START_APP).

#### 2. Stop the running application by container name pattern:
echo "Stopping {{APPLICATION_NAME}} services..."
containers=$(docker ps -q --filter "name=${NAME_OF_APPLICATION}-.*-${USER_ID}-.*")
if [[ -n "$containers" ]]; then
    docker stop $containers
    docker rm $containers
    echo "Services stopped successfully"
else
    echo "No running containers found for USER_ID: $USER_ID"
fi

After completion, verify networks are removed, volumes are preserved, and report the final status.

5. Making Backups (and Restoring)

Back up application databases to OVH S3-compatible object storage, restore them when needed, and clean a database safely. The backup lifecycle: dump the database with pg_dump, sync the dump to OVH S3, download it when needed, and restore it into the database container.

flowchart LR
    DB[(PostgreSQL in container)] -->|pg_dump| Dump[backup_YYYYMMDD.sql]
    Dump -->|aws s3 sync| S3[(OVH S3 bucket)]
    S3 -->|aws s3 cp| Local[restore.sql]
    Local -->|psql| DB2[(PostgreSQL in container)]

The backup lifecycle: dump, sync to OVH S3, download, and restore.

# Backup a PostgreSQL database
docker exec <db_container> pg_dump -U postgres <database> > backup_$(date +%Y%m%d).sql

# Sync backups to OVH S3 object storage
aws s3 sync ./backups/ s3://<bucket_name>/backups/ \
  --profile OVH-SWAUTOMORPH \
  --endpoint-url https://s3.gra.io.cloud.ovh.net/

# Download and restore
aws s3 cp s3://<bucket_name>/backups/backup_20240101.sql ./restore.sql \
  --profile OVH-SWAUTOMORPH \
  --endpoint-url https://s3.gra.io.cloud.ovh.net/
docker exec -i <db_container> psql -U postgres <database> < restore.sql

Skill configuration: BACKUP_DATABASE

The database backup action is driven by the BACKUP_DATABASE agent skill, which dumps the PostgreSQL database and uploads the archive to OVH S3.

View the BACKUP_DATABASE skill prompt (SKILL.md) 
You are an autonomous IT Operater agent with access to execute shell commands on a Linux server.
Please backup the PostgreSQL database by executing these steps:
- Backups are stored in OVH S3 using IPv4 addressing
- The S3 bucket path follows: s3://bucket-name/{{APPLICATION_NAME}}/{{IPv4_ADDRESS}}/backups/

#### 1. Check Prerequisites: docker, docker-compose, aws cli.
#### 2. Retrieve DB configuration (DB_CONTAINER, DB_NAME, DB_USER) from docker-compose.yml, falling back to .env.prod.
#### 3. Get the server IPv4 address.
#### 4. Create ./backups and a dated backup file name.
#### 5. Execute the backup:
docker exec $DB_CONTAINER pg_dump -U $DB_USER $DB_NAME | gzip > $BACKUP_FILE
#### 6. Upload to OVH S3:
aws s3 cp $BACKUP_FILE "s3://${S3_BUCKET}/${NAME_OF_APPLICATION}/${SERVER_IP}/backups/" --acl private
#### 7. Record the backup in deployment history.
#### 8. Clean up local backups older than 7 days.

Finally, display the backup file, S3 location, size, and deployment id.

Skill configuration: RESTORE_DATABASE

The restore action is driven by the RESTORE_DATABASE agent skill, which downloads a backup from OVH S3 and restores it into PostgreSQL after taking a safety backup.

View the RESTORE_DATABASE skill prompt (SKILL.md) 
You are an autonomous IT Operater agent with access to execute shell commands on a Linux server.
Please restore the PostgreSQL database by executing these steps:
#### 1. Check Prerequisites: docker, docker-compose, aws cli.
#### 2. Retrieve DB configuration from docker-compose.yml / .env.prod.
#### 3. Get the server IPv4 address.
#### 4. List available backups from OVH S3.
#### 5. Download the backup (defaults to the latest if {{BACKUP_FILE}} is not specified).
#### 6. Stop application services to prevent conflicts.
#### 7. Create a safety backup of the current database.
#### 8. Drop and recreate the database.
#### 9. Restore from the backup file:

#### 11. Verify the database connection.

On failure, automatically restore from the safety backup.

6. Modifying Applications

Use AI-powered tools (the Shai CLI) to modify, customize, and extend deployed applications. The AI-assisted workflow: describe the change, review the generated code, validate it in staging, roll back on failure, and deploy to production once it passes.

flowchart TD
    Identify[Identify the app and the change needed] --> Describe[Describe the change to Shai CLI]
    Describe --> Review[Review the generated code changes]
    Review --> Staging[Apply and test in a staging environment]
    Staging --> OK{Tests pass?}
    OK -->|no| Rollback[Roll back the change] --> Describe
    OK -->|yes| Prod[Deploy to production]

The AI-assisted modification workflow.

  1. Identify the application and the change needed
  2. Describe the modification to the Shai CLI
  3. Review the generated code changes
  4. Apply and test in a staging environment
  5. Deploy to production once validated (roll back on failure)

Skill configuration: MODIFY_CODE / KILL

When a modification requires an immediate teardown, the KILL skill forcefully terminates the application's containers (SIGKILL) and removes them while preserving named volumes — unlike the graceful STOP_APP.

View the KILL skill prompt (SKILL.md) 
You are an autonomous Operations agent running on a Linux server.
This skill forcefully kills all running Docker containers of a deployed application
instance for a given user (docker kill / SIGKILL), then removes the dead containers.
Named volumes and data are preserved; unsaved in-memory state is lost.

#### 1. Calculate HTTP Ports (same logic as START_APP).
#### 2. Identify the target containers by name pattern ${NAME_OF_APPLICATION}-.*-${USER_ID}-.*.
#### 3. Forcefully kill and remove the containers:
docker kill $containers
docker rm -f $containers
#### 4. Verify no matching containers remain and report the result.

Use KILL only when an immediate termination is required.

7. Controlling AI Agents

Granting an agent autonomy is a governance decision, not a technical one. This section shows how to keep an agent useful without letting it act beyond its mandate: place operations on the autonomy spectrum, decide where approval gates belong, name the guardrail layers that wrap every action, and judge what must stay human-in-the-loop. The examples come from the OPCP-EXPLORER platform, whose virtual agents — a Developer agent that modifies code and an Operations agent that runs START, STOP, RESTART, PS, and LOGS — act on real deployments.

The Autonomy Spectrum

Autonomy is a spectrum, not a switch. Each step to the right grants more freedom and removes a point of human control, so each step must be earned by lower risk or stronger guardrails.

  1. Suggest — the agent proposes; a human performs every action.
  2. Confirm each step — the agent acts, but a human approves before each action. Billing-affecting START/STOP fits here.
  3. Act with checkpoints — the agent runs several steps, pausing at defined checkpoints (deploy to staging automatically, pause before production).
  4. Act and report — the agent completes the task and reports afterward; a human can intervene or revert.
  5. Fully autonomous — the agent acts without review inside its granted scope.

Approval Gates

An approval gate is a point where an action pauses until a human signs off. Place a gate wherever an action is hard to reverse, costs money, or widens access: admin-only destructive actions (delete an application, destroy a GPU/MIG instance), billing-affecting operations (START/STOP), and production promotion.

Guardrail Layers

Guardrails constrain every action regardless of whether a human is watching. They map directly onto OPCP-EXPLORER's security features.

LayerWhat it constrainsOn OPCP-EXPLORER
PermissionsWhich actions are allowedUser isolation with separate deployment directories; admin-only destructive endpoints
ValidationThe shape and safety of inputsInput validation, SQL-injection prevention, path-traversal protection
Limits / TimeoutsHow long and how far an action runs30-minute operation timeout with process-group termination; read-only, no-network serverless jobs
ObservabilityThat every action is auditablePrompt logs and billing_activities.log
Kill switchThe ability to stop everything at onceProcess-group termination and graceful degradation

Human-in-the-Loop

Human-in-the-loop (HITL) is the policy that some actions must not proceed without a person in the decision. Reserve mandatory HITL for actions that are irreversible, security-sensitive, or costly, and treat graceful degradation (falling back to a safe reduced mode) as a safety default.

Key Takeaways

  • Installation, registration, start, stop, backup/restore, modification, and agent governance form one continuous operations lifecycle on OPCP-EXPLORER.
  • Each operation is automated by a named agent skill (START_APP, STOP_APP, BACKUP_DATABASE, RESTORE_DATABASE, CLEAN_DATABASE, MODIFY_CODE/KILL, AGENTS_CONTROL, STATUS_APP) with a fixed, auditable prompt.
  • Mutating actions — start, stop, kill, clean, lifecycle control — require confirmation and sit behind approval gates; destructive ones stay human-in-the-loop.
  • Guardrails (permissions, validation, limits/timeouts, observability, kill switch) wrap every action regardless of autonomy level.
